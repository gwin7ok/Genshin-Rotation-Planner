## 2. なぜ自動探索は「手動ローテ」に勝てないのか？（課題の構造）

手動で組まれた優秀なローテーションと自動探索（特に単純な全探索・貪欲法・固定テンプレ順）の間にDPSの差が生まれる理由は、主に以下の4点に集約されます。

1. **「局所最適」では組めない要素が多すぎる**
   * 例：「今はダメージが出ないが、先にAのスキルで元素下地を付け、Bで拡散し、Cでバフを撒いてからD（スナップショット持ち）が爆発を撃つ」といった**数手先の先行投資（セットアップ）**は、目先のDPSを基準にする貪欲法では絶対に見つかりません。
2. **WASM版 gcsim の評価コストによる探索空間の制限**
   * gcsim は精度が極めて高い反面、ブラウザ上の WebWorker で1回回すだけでも数万通りの全通りを評価する時間は取れません。探索回数が限られる中で「デタラメな順列」を gcsim に投げても、探索予算を浪費してしまいます。
3. **時間調整（パディング）とCT境界の微調整**
   * 手動ローテは「CTが残り1.2秒足りないから通常攻撃を2回挟む」「キャラ切替CT（1秒）に引っかからないようにN1を挟む」「2ローテに1回だけ爆発を撃つ」といった**微細な時間調整**で1周の秒数（$T_{\text{rot}}$）を極限まで詰めています。アクションの並びだけを探すと、こうした隙間埋めや間引きができません。
4. **「エネルギー循環（ER）」と「火力」のトレードオフ**
   * 手動ローテでは「ベネットEの粒子を香菱で受け取る」ことで香菱のチャージ要求を下げ、その分火力を出したり、そもそも2周目が破綻しない動きを選びます。

## 3. 手動同等以上のDPSを出すために導入すべきロジック

WebAssembly版 gcsim をエンジンとし、すでにアプリ側で「フレーム長・CT・バフ継続時間・役割・必要ER」のデータを保持している本ツール の強みを最大限に活かすなら、以下の**4つのロジック**を組み合わせて導入するのが最も効果的です。

### 導入すべきロジック①：2段階評価（高速サロゲート枝刈り ＋ gcsim WASM本評価）
gcsim を探索ループの最初から毎回回すのではなく、**「アプリ側が既に持っているフレーム・CT・バフ継続時間データ」を使った超高速な事前評価（サロゲートモデル）**を前段に挟みます。

* **Stage 1（JS上の軽量計算：1件あたり数マイクロ秒）**
  * gcsim を呼ばずにガントチャート相当のタイムラインだけを仮組みし、以下を高速計算します。
    * **バフ重複スコア**：メインアタッカー（パワースパイク）の出場フレームに対して、サポートのバフ・デバフが何％重なっているか。
    * **スナップショット整合性**：スナップショット対象アクション（例：香菱Qなど）の開始フレーム時点で、主要攻撃バフが有効になっているか。
    * **CT・エネルギーペナルティ**：1周完了時点でCT待ち・切替1秒CT衝突・エネルギー不足（粒子収支の破綻）が起きていないか。
    * **アイドル時間ペナルティ**：バフが残っているのに空白時間が生じていないか。
* **Stage 2（gcsim WASM 実行：上位候補のみ）**
  * Stage 1 のスコア上位（かつ多様性を残した）数個〜数十個のみを WebWorker（可能なら複数Worker並列）で gcsim に投げて実測DPSを出します。

これにより、**限られた時間内で実質的に数千〜数万パターンの探索と同等のカバレッジ**を得られます。

---

### 導入すべきロジック②：「単発アクション」ではなく「コンボ・マクロブロック」＋「部分入れ替え」の探索
1つ1つの行動（スキル・爆発・通常1〜3・重撃など）をゼロから並べるのではなく、探索の単位を**「意味のある最小ブロック」**に構造化しつつ、後から解体・再配置できるハイブリッド構成にします。

1. **役割（Role）に依存しすぎないブロック設計**
   * 「サポーター1 → サポーター2 → サブアタッカー → メインアタッカー」のような**固定の役割順テンプレートは、Wアタッカー編成・クイックスワップ編成・万葉の2元素同時拡散セットアップなどで手動に負ける原因**になります。
   * 代わりに、各キャラが持つ行動を以下のブロックに分解し、**「バフ継続時間」と「反応セットアップ」の制約内で自由に並べ替える**ようにします。
     * **セットアップ／下地ブロック**（短時間付着や特殊スキル）
     * **バフ／設置ブロック**（E/Qセット、またはEとQを分離）
     * **パワースパイク／出場コンボブロック**（例：N3D×3、重撃ループなど）
     * **粒子生成／回収ブロック**（CTが短いE単体など）
2. **「EとQの分離」と「2ローテに1回」の選択肢**
   * キャラによっては「E→Q」を連続で撃つより、「1回目にE、他キャラを挟んでからQ」や「粒子を別キャラに渡すためQ→Eで即交代」、「重すぎる爆発は2ローテに1回だけ撃つ（15秒ローテ等）」方が高DPSになるケースが多々あります。**1キャラの能力を1ブロックに縛らず、分割・間引きを探索オプションに含める**ことが手動超えの鍵になります。

---

### 導入すべきロジック③：ドメイン特化型の「近傍改善（局所探索 / ミーム探索）」
手動でローテーションを改善するとき、人間はゼロから組み直さず「今のローテの一部をちょっと直す」という思考をします。これと同じ**「意味のある変形ルール（近傍操作オペレータ）」**を定義し、ビームサーチや焼きなまし法・局所探索（Hill Climbing / Tabu Search）として回します。

実装すべき具体的な変形オペレータの例：
1. **継続時間順・スナップショット修復オペレータ**
   * バフAの効果がアタッカーの後半で切れている場合、Aのブロックを後ろにずらす／継続時間の長い順に並べ替える。
   * スナップショット持ちの行動がバフより前にあれば、バフ直後にスワップする。
2. **通常攻撃・ダッシュパディング（隙間埋め／CT調整）オペレータ**
   * 次の行動のCTが数フレーム〜1.5秒足りない、あるいは切替1秒CTに引っかかる箇所に、`attack:1`〜`attack:3` やダッシュを自動挿入する（逆に、不要な待機・過剰な通常攻撃を削ってローテ時間 $T_{\text{rot}}$ を短縮する）。
3. **粒子受け渡し（Funneling）最適化オペレータ**
   * gcsim 結果（または仮計算）で特定キャラのエネルギーが不足している場合、
     * 粒子生成スキル（または西風持ちの通常攻撃）の**直後の交代先**をエネルギー不足キャラに変更する。
     * ローテ末尾に「CTが上がったスキルの追加使用＋受け取り交代」を1セット挿入する。
4. **アクション圧縮・カットオペレータ（冗長行動の削除）**
   * ローテ全体のDPSを下げている「火力の低いスキルの空撃ち」や「必須でないサポートの重すぎる爆発（カットイン時間によるDPSロス）」を1つ削除して $T_{\text{rot}}$ を短縮し、DPSが上がるかテストする。

---

### 導入すべきロジック④：目的関数（評価指標）への「必要ER・ループ成立条件」の統合
「1ローテ目だけ爆発を全部撃って終わり」のローテーションは、数値上は高く見えても実戦（および多ローテ平均）では破綻します。また、手動の優秀なローテは**「チャージ要求を現実的なラインに抑え、その分アタッカーやサブアタッカーの火力に還元している」**という特徴があります。

* **複数ローテ（または定常ループ状態）での評価**：
  * 探索の評価値には必ず「2〜3ローテ目までエネルギー破綻せずループできるか（`scripts/check-required-er.ts` 相当の判定）」を含め、エネルギー不足には強いペナルティを与える。
  * （※「幽境モード」など立ち上がり重視モードの場合は、初期エネルギー0状態からの2ローテ合計ダメージ／クリアタイムを直接評価する形式に切り替える）
* **ERコスト込みの実質DPS評価（オプション）**：
  * もしキャラのビルドが固定で「チャージ不足で動けないローテ」が弾かれてしまうなら、探索中に「あと少しERがあれば回るのに」という惜しい候補をすぐ捨てず、**（オプション機能として）必要ERを達成するためのサブステ換算ペナルティを差し引いた期待DPS**で比較すると、「実は粒子受け渡しを少し変えるだけで爆伸びする黄金ローテ」を取りこぼさなくなります。

## 1. ツールの全体像と現在の自動探索の到達点

### ツール基盤の強み
* **精緻なアプリ内タイムライン計算（`rotationCalculator.ts` 等）**：60FPS基準のフレーム、ヒットラグ、スキルストック、モード維持/再発動（`mode.repress`）、特殊スキル/特殊爆発枠、祭礼リセット、風共鳴CD倍率、持ち越し（`carryOver`）まで完全にモデリングされています。
* **ブラウザ完結の WebAssembly版 gcsim 連携（`buildGcsimConfig.ts` / `dpsCalc.ts` / `requiredEnergyRecharge.ts`）**：画面では Web Worker、Node検証では `worker_threads` で同一の `main.wasm` を並列実行でき、キャラ別DPS・エネルギー待ちフレーム・必要ERの3段階（目安/安定/確実）算出・幽境モード（`startEnergyZero` 等）まで完備されています。

### 現在の自動探索（`rotationSearch/`）の仕組みと課題
現在の `search.ts` は以下のパイプラインで動作しています。
1. **候補生成（`candidates.ts`）**：`characterRoles.ts` の役割（`attacker` / `subAttacker` / `supporter`）割り当てごとに、「サポーター → サブアタッカー → アタッカー」の順で並べ、`FILL_TEMPLATES`（9種）から候補を生成（`MAX_USES=260`・`MAX_ORDERS=6`・全体上限20,000件で等間隔間引き）。
2. **フィルタ＆簡易スコア（`evaluate.ts`）**：`calculateRotation` で CT 違反（4件超）と非CT警告を弾き、`attackerFraction * (1 + 0.25 * overlapPerSecond)` で採点。
3. **探索本体（`search.ts`）**：役割グループごとの貪欲被覆を含めて `keep1=900` 件を `runs1=1`（最大60秒）で実行 → ④a キャラ別最適使い方の組み合わせ追加 → ④b ビーム山登り（`BEAM=4`, `REFINE_BATCH=70`, 予算700） → ⑤ 上位12件を `runs2=10` で本検証。

**現状の壁（`plan.md` と手組みプリセットの比較から見えるギャップ）：**
* `simpleScore` と gcsim 実測DPSのスピアマン順位相関が **0.2〜0.3** 程度しかなく、近傍探索のバッチ（70件）や初期候補の足切りで本命候補が落ちやすい。
* 手組みプリセット（`raiden-national.json`、`furina-vaporize.json`、`keqing-intensify.json`、`sandrone-stellar-conduct.json`）が採用している動きのうち、**現在の `candidates.ts` / `NEIGHBOR_STEPS` では構造上そもそも作れない・辿り着けないパターン**が複数存在する。

## 2. 手動同等以上のDPSを出すために導入すべき7つのロジック

前回の一般提案（構造化マクロ、2段階評価、近傍改善、エネルギー循環統合）を、**このリポジトリのコード・データ実態に合わせて具体化した改善案**です。

---

### ロジック①：手組みプリセットに存在する「未生成アクション・順序」の解放（`candidates.ts`）

手組みプリセット4種と `candidates.ts` を比較すると、以下の致命的な欠落が見つかります。

1. **`dash`（ダッシュキャンセル）と固有派生アクションが生成・近傍に無い**
   * `raiden-national.json` の雷電将軍は **`N5D × 3`（ダッシュキャンセル）** を使っていますが、`FILL_TEMPLATES` にも `NEIGHBOR_STEPS` にも `dash` がありません。胡桃の `N1CD` 等でも必須となるため、テンプレートに `['n', 'ca', 'dash']` / `['n', 'n', 'n', 'n', 'n', 'dash']` 等を加え、`NEIGHBOR_STEPS` にも `'dash'` を入れるべきです（`jump` キャンセルも含め、武器種/キャラ特性で選択）。
   * `actionMapping.ts` にある固有アクション（例：早柚の `e_shorthold` / 雲菫等の段付き長押し / 特殊スキル `e_spearstorm`・`e_specialskill` / 特殊爆発 `q_special` / サンドローネの `ca_beams*`） も、`useOptions` や `NEIGHBOR_STEPS` が `'e'`, `'e_hold'`, `'e_recast'`, `'q'`, `'ca'` しか見ていないため探索から漏れています。`availableActions` の定義を走査して、存在する派生アクションを自動で候補・近傍の語彙に組み込む必要があります。
2. **`useSteps` の `E → Q` 固定を解除する**
   * 現状 `useSteps` は `[...u.es, ...(u.q ? ['q'] : [])]`（常に E→Q）ですが、手組みの `raiden-national.json` のベネット（`Q → N → tE`）、`furina-vaporize.json` の早柚（`Q → hE`）、`sandrone-stellar-conduct.json` の七七（`Q → E`）はすべて **`Q → E`** です。粒子を受け取るタイミング、爆発カットイン中の裏効果発生、教官/旧貴族バフの発動順で大きく差が出るため、EとQを両方使う場合の選択肢に **`Q → E` を最初から含める**（あるいは山登りで最優先近傍にする）べきです。
3. **長押し秒数（`HOLD_FRAMES_ACTIONS`）の扱い**
   * `furina-vaporize.json` の早柚のように長押しスキル（`hE` 8.4秒）でダメージ・拡散を稼ぐキャラは、`buildGcsimConfig.ts` に `holdSecondsByActionId` を渡さないと `hold=1`（最短長押し）になってしまいます。`HOLD_FRAMES_ACTIONS` 対象アクションについては「短め（1f〜1s）」と「最大維持（`maxFrames`）」の両方を候補化する仕組みが必要です。
4. **gcsim 実行エラーの事前フィルタ強化**
   * `plan.md` で問題になっていた「サンドローネの E なし重撃 decode エラー」「ラウマの草露不足（`Cannot use Skill Hold without Dew`）」に加え、`CHARGE_REQUIRES_ATTACK` に該当する58キャラの `ca` 単体使用を `candidates.ts` / `neighborsOf` 側で事前ブロック・自動補正（前に `n` を自動付与）することで、`quickFailed` や `refine` 予算の空費を防げます。

### ロジック②：複数回出場（再出場）と「条件付き連携効果」からのマクロ部品構築（`candidates.ts`）

* **現状の制約**：`candidates.ts` の初期生成ではサポーター/サブアタッカーは1ローテに1回しか登場できず、アタッカーも1回の分割しか試せません。しかし `keqing-intensify.json`（激化刻晴）を見ると、`刻晴[EE] → ナヒーダ[tE Q] → フィッシュル[Q] → 万葉[N tE hP] → 刻晴[EE N C Q] → 万葉[tE hP] → 刻晴[EE (NC)×3 EE]` のように、**CTが短いキャラ（万葉・刻晴）がローテ中に2〜3回出場して翠緑4やバフを更新し直すクイックスワップ構造**をとっています。
* **導入すべきロジック**：
  * サポーター/サブアタッカーのうち「スキルの CT が `targetSeconds / 2` 以下（例：CT 4〜10秒以下）」のキャラについては、**「後半（アタッカーの出場間や末尾）にスキルだけの2回目出場を挟む」枠**を初期候補または専用のマクロ近傍オペレータとして用意します。
  * さらに `plan.md` 末尾で課題として挙げられていた通り、マスターデータの `mode.repress`（例：ニィロウ `E×4`）、`mode.special`（特殊スキル→特殊爆発のセット：フリンズ・ヴァレサ）、`mode.repress.followUps`、および `startsSpecialPool` を解析し、**「単発アクション」ではなく「効果を発動させる最小コンボ部品（例：ラウマなら草系キャラの後＋`e_hold → q`、フリンズなら `e → e_spearstorm → q_special` 等）」**を自動生成して初期シードに組み込むことで、1手ずつの山登りでは到達できない複合コンボを1発で拾えるようになります。

### ロジック③：簡易スコア（`simpleScore`）の抜本的改良（`evaluate.ts`）

現在 `plan.md` で「順位相関 0.2〜0.3 で当てにならない」となっている理由 は、`evaluate.ts` のコードを見るといくつかの明確な原因に分解できます。

1. **「CT 違反の待ち時間」をスコアの時間計算に反映させる**
   * `calculateRotation` は CT 違反があっても待機を入れず時刻を進めてしまうため、`TOLERATED_CT_ISSUES = 4` を許すと **「実際は gcsim 上で CT 明けまで5秒待たされて DPS が激減するローテ」ほど、見かけの `totalDuration` が短くなって `attackerFraction` が高くなる（簡易スコア上位に偽の強候補が並ぶ）** 現象が起きます。
   * **改善案**：`evaluate.ts` 内で `result.validationIssues` の CT 違反秒数（または `actionFlow` での待ち発生）を `totalDuration` に加算した**「実効ローテーション時間 `effectiveTotal`」**で `attackerFraction` やスコアを算出し、さらに待ちの間に消えるバフの重複時間も補正することをおすすめします。
2. **「全バフ一様カウント」から「バフの質・スナップショット・サブアタッカー火力」への重み付け**
   * 現状 `simpleScore` は「アタッカー表時間中の他キャラのバフ/パッシブ重複秒数」をすべて同じ重み `1` として加算しており、かつアタッカー以外の火力（香菱・八重神子・オズ等）へのバフを一切評価していません。
   * **改善案**：
     * すでに `effectNature.ts`（`stat` / `cooldown` / `heal` / `energy` / `attack`）の分類基盤があるため、**回復・エネルギー系のバーは重複スコアから除外（または低重み）**し、`stat` / 耐性ダウン・継続ダメージスキルに重みを寄せます。
     * `solo-dps.ts` の思想を活かし、**キャラの役割・スキル/爆発の重要度（特にスナップショット持ちや高シェアなサブアタッカーの設置タイミングにバフが乗っているか）**を加点対象にすると、ベネット→香菱や万葉の拡散タイミングが簡易スコアの段階で正しく上位に来るようになります。
     * 「行動のモーションDPS密度（スキル・爆発・重撃・落下などのダメージ行動率 vs アイドル・冗長移動）」の項を入れると、意味のない通常連打の引き延ばしを弾けます。

### ロジック④：探索時の戦闘時間（60秒固定）による「端数歪み」の排除（`search.ts`）

現在の `search.ts` では探索中（④・④b）に `EXPLORE_SECONDS = 60` 秒・`runs1 = 1` 回で実行していますが、これには構造的な歪みがあります。
* 例：19秒ローテと21秒ローテを「60秒固定」で切ると、19秒ローテは3周目のパワースパイクがまるごと入る（57秒で完了）のに対し、21秒ローテは2周＋バフ準備だけして時間切れになり、**実際の定常DPSは21秒の方が高くても、60秒打ち切りでは大きく負ける**ことがあります（これが `plan.md` で「60秒3回で勝った候補が、120秒10回では下がる」一因でもあります）。
* **改善案**：
  * 探索中（④・④b）の比較では固定60秒で切るのではなく、**「アプリ見積りのローテーション長（`totalSeconds`）をもとに、50〜60秒前後に最も近くなる『ちょうど整数周（例：2〜3周）』が終わる時刻」**をその候補の `battleSeconds` に渡す（あるいは `dpsCalc.ts` で「初動＋ループ2周」など周数ベースで評価し、実際の経過時間 `seconds` で割る）ことで、**ローテーション境界の切り捨てノイズを完全に除去**できます。
  * （※「幽境モード」やタイムアタック設定でユーザーがあえて厳密な `60s` 等を指定したい場合のみ、最終検証の ⑤ で指定 `battleSeconds` を使う二段構えにするのが理想的です。）

### ロジック⑤：1手山登りの局所解を破る「2手複合近傍」と「部分交叉（ミーム探索）」（`candidates.ts` / `search.ts`）

`plan.md` で「1手ずつの山登りでは届かない複合変化がある」と的確に分析されていますが、④b の山登りにもいくつか拡張余地があります。

1. **バッチ上限（`REFINE_BATCH = 70`）の切り方を変える**
   * 現状 `neighborsOf` が数百個の近傍を生成したあと、`ev2.scored.slice(0, 70)` と**当てにならない簡易スコア順で上位70個だけ**を切り出して実行しています。これだと「`simpleScore` からは評価されにくいが良い近傍（例：Qを消して時間を縮める、1つスキルを増やす、順番を入れ替える）」が71位以降に落ちて試されない恐れがあります。
   * **改善案**：近傍の種類（`swapStint` / `deleteAction` / `moveAction` / `insertAction` / `splitMerge`）ごとに均等に枠を配分する（層化サンプリング）か、③で改良したスコアを使うべきです。
2. **「上位候補間の部分交叉（Crossover）」の導入**
   * ④a の「キャラごとの使い方の平均トップを組み合わせる」アプローチは非常に有効ですが、順序やアクションの細かい配列までは引き継げません。④b の山登りで各グループの上位候補（または異なるグループの優秀な部分構造）が出揃った段階で、**「候補Aのサポート前半 ＋ 候補Bのアタッカー後半」を合成する交叉（Crossover）**を数件試すだけで、2〜3手同時に変わるジャンプが簡単に発生します。
3. **2手同時変形の特定オペレータ**
   * 「キャラの出場位置を後ろに動かしつつ、同時に末尾の `n` を消す」「`e` を足した分だけ重複した `n` や `ca` を1回削ってローテ長を保つ」といった**ローテ長を維持したまま行う2手スワップ**を入れると、CT境界を壊さずに最適解へ跳べます。

### ロジック⑥：gcsim 実行ログを使った「診断駆動型（Feedback-Guided）の近傍生成」（`search.ts` / `dpsCalc.ts`）

現在の `search.ts` は `computeDps` から `dps.mean` と `dps.sd` だけを受け取っていますが、**`dpsCalc.ts` はすでにキャラ別の詳細集計（`byChar` のダメージシェア・`energyWaits`・CT待ち/実行ログ）を計算できる基盤**を持っています。

これを探索の近傍生成にフィードバックすることで、闇雲な70近傍の試行から**「弱点をピンポイントで直す探索」**へ進化できます。
* **低ダメージシェアキャラのアクション削減**：`byChar[i].share` が極端に低いサポーター（例：5%未満）が長いカットインの `Q`（約1.8〜2.0秒）や複数回の `E` を撃っている場合、そのキャラの `Q` を削除する近傍に高い優先度を付ける。（`plan.md` で八重・オデットの Q を抜いて大幅上昇したケース を自動化できます）
* **実測CT待ち・スタミナ待ちの自動解消**：gcsim のログで `could not execute ... action not ready`（CT待ち）が出たアクションが特定できたら、その直前に `n`（時間稼ぎ）を挿入する／前のアクションを削除せず後ろへずらす／該当キャラを後ろの Stint へ移動する近傍を優先生成する。
* **高ダメージシェアキャラのバフ重複チェック**：`byChar` 上位1〜2名のキャラ（メインアタッカーだけでなく香菱・八重神子などの主力サブアタッカーも含む）の出番・スキル発動時刻に対して、サポーターのバフが残っていなければ出場順を近づける。

### ロジック⑦：エネルギー収支（必要ER）との統合（実戦再現性の担保）

現在、`search.ts` は `ignoreBurstEnergy: true`（エネルギー無視）で最適化しているため、極端な話「全員のERが全く足りず実戦（やアプリで「エネルギー考慮ON」のDPS計算）では全く回らないローテーション」でも1位に出てしまいます（`AutoSearchDialog.tsx` で注記している状態）。

* **導入案1：粒子受け渡し（Funneling）の近傍オペレータ**
  * たとえ `ignoreBurstEnergy: true` で探すとしても、`requiredEnergyRecharge.ts` の `collectEnergyTimelines` 相当のロジックを上位候補（ステージ④以降や⑤の前）に1回だけ通せば、**「各キャラの必要ER」と「設定ビルドの現在ERとのギャップ」**が即座に分かります。
  * もし特定キャラのERが不足していれば、そのキャラの直前に他キャラの粒子生成 `E` を移動する（粒子受け渡し）近傍を生成したり、UI上で「このローテは〇〇のERが+30%不足／達成済み」を結果テーブルに表示したりできます。
* **導入案2：「エネルギー考慮（`ignoreBurstEnergy: false`）」探索モード／ペナルティの選択**
  * 持ちキャラ装備（`build`）や実戦的な仮値を使う場合、⑤の検証フェーズやオプション設定で **`ignoreBurstEnergy: false`（`dpsCalc.ts` の通常モードと同じ条件）での実質DPS、および `energyWaitFrames` によるペナルティ評価**を選べるようにすると、「チャージ込みで実際に最も速く回る手動超えローテーション」を自動発見できるようになります。

## 3. 実装の優先順位（ロードマップ案）

現在の完成度と費用対効果（開発コストに対するDPS改善幅・探索時間短縮）を考えると、以下の順で手を入れるのが最も効果的です。

1. **【最優先・即効性大】候補生成の制限解除とエラー事前防止（`candidates.ts`）**
   * `useSteps` に `Q → E` の並びを追加。
   * `FILL_TEMPLATES` と `NEIGHBOR_STEPS` に `dash` キャンセルと `actionMapping.ts` にある固有派生アクション（特殊E/Q、長押し等）を組み込む。
   * `CHARGE_REQUIRES_ATTACK` 等の実行エラー条件を `candidates.ts` / `neighborsOf` 側で事前排除し、`quickFailed` の無駄をなくす。
2. **【高効果】探索中評価の「整数周回ベース化」（`search.ts`）**
   * `EXPLORE_SECONDS = 60` 打ち切りによる端数歪みをなくし、整数周回（または周数指定）で比較することで、`runs1 = 1` の探索とビーム山登りの精度を一気に引き上げる。
3. **【中〜大効果】`simpleScore` の修正とCT待ち時間の反映（`evaluate.ts`）**
   * `simpleScore` の分母に CT 違反の待ち秒数を加算し、`effectNature.ts` を使って無関係なバフを除外、主力サブアタッカーやスナップショットを加味することで相関 0.2〜0.3 の壁を破る。
4. **【決定打】gcsim ログフィードバック＆部分交叉（`search.ts` / `dpsCalc.ts`）**
   * `byChar` シェアに基づく低寄与 Q の削減優先、実測 CT 待ち箇所の修復近傍、および上位候補間の交叉を取り入れ、複合条件（ニィロウ/ラウマ型やクイックスワップ型）を安定して攻略する。
5. **【実用完成】ER（エネルギー収支）との統合（`requiredEnergyRecharge.ts` 連携）**
   * 上位候補の必要ERチェック／実質（`ignoreBurstEnergy: false`）DPSでの比較オプションを追加。

このアプローチにより、現在の「1回×900件の広い出発点 ＋ ビーム山登り」という優れた基盤を活かしつつ、手組みプリセットのような高度なキャンセル・反応セットアップ・エネルギー最適化を含んだローテーションを安定して見つけられるようになります。
