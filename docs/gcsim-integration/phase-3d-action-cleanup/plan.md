# フェーズ3d 計画: アクションの整理（gcsim が自動で切り替えるものを統合）

関連決定: D25（自動切り替えは別アクションにしない）、D26（通常攻撃は「N」1つ）、D27（CTの規則辞書・N の時間の上書き）、D30（規則辞書の形式）、D31（次の行動別のキャンセルフレーム）
前提フェーズ: フェーズ3、3b、3c、4（変換処理の対応表を更新する）
後続フェーズ: フェーズ6（書き戻し。アクションの対応が単純になる）

## 目的

ユーザーが追加できるアクションを、**gcsim に渡す命令と1対1**に近づける。gcsim が状態で自動的に別モーションへ切り替えるものは、別のアクションとして持たず、通常のボタン（N・E など）にまとめる。

- ユーザーの操作が gcsim の設定文とそのまま対応し、「指定と実際の動作の食い違い」（例: 「N2 単独」「露あり重撃を選んだが gcsim 側に露がない」）が起きなくなる。
- ボタンが減り、ユーザーが迷わない。

## 対象（調査結果: 2026-09-29）

### 1. 元素スキル(E)の派生アクション 27 個（20 キャラ）

| **B: gcsim へのパラメータ指定が必要**（`skill[recast=1]` など） | 9 | **別ボタンのまま維持**（D26） |

### 2. 通常攻撃 N1〜Nn を「N」1つにまとめる（D26）

- gcsim は `attack` を繰り返すだけで、段（N1→N2→…→最終段→N1）を自動で進める。連続した通常攻撃でなくなる（他のアクションを挟む・交代する）と1段目に戻る。
- アプリのボタンは **「N」だけ**にする。連続した N の何段目かは、**計算時に自動で数える**（gcsim と同じ規則）。最大段数を超えたら1段目に戻る。
- 各段の所要時間は、マスターデータの段ごとの値（今の N1〜Nn の値）を使う。ユーザーが個別に変えた所要時間は、アクション（インスタンス）ごとにそのまま残す。
- 記法・手順書は、段数を含めず「N」で表示する（記法は今も `shortName` の「N」を並べている）。

## 設計の要点

### マスターデータ
- N: `_n` を1つ生成する。段ごとの値（所要時間・フレーム）は、そのアクションに配列で持たせる（例: `normalHits: [{ duration, frames }, ...]`）。今の `_n1`〜`_nK` は生成しない。
- E: A の派生アクションは生成しない。E の所要時間・CT・効果時間は、最初の E の値を使う。派生の値はフェーズ6の書き戻しで、実行後に合わせる。
- 凸データの `actionChanges`（効果時間の延長）が参照するアクション ID は、A に含まれるものが無いことを、生成時のレポートで確認する（現在の対象は `e` / `q`）。

### 計算（`rotationCalculator.ts`）
- N のインスタンスは、出場ブロックの中で「直前が N の連続なら段+1、それ以外は1段目」として段を決め、その段の所要時間を使う。インスタンスの `duration` が未指定なら自動（段で決まる）、指定があればその値（ユーザーの編集）。**gcsim の結果の書き戻し（D20）は、編集済みでも最優先で上書きする**（D27）。
- ニィロウ等の状態依存（E後の N が剣舞になる）は、gcsim の実行結果の書き戻し（フェーズ6）で実際の時間に合わせる。実行前の見積りは、通常の N の値を使う。

### CT: 規則辞書（実行前の概算）と書き戻し（実行後）の併用（D27）

E が1つのボタンになると、アプリは「最初の E」と「状態で切り替わった E（ステップ・再発動など）」を区別できず、そのままでは全ての E がCTを開始する扱いになり、CT違反の判定を誤る。次の2つを併用する。

1. **実行前の概算: アクション状態の規則辞書**（案A）
   - キャラごとに「この E は、直前の E から○秒以内ならCTを開始しない（または CT が△秒）」のような規則を、辞書（データファイル）として持つ。アプリの時間計算（`rotationCalculator.ts`）は、この辞書を使って、状態で切り替わった E のCTを判定する。
   - 規則のイメージ: `{ キャラ ID, 窓を開く E のアクション ID, 窓の長さ(秒), 窓の中の E の扱い: { cooldown: 0 } }`。ニィロウなら「E（CT 18秒）の発動から 10 秒以内の E はCTを開始しない（`cooldown: 0`）」。
   - 辞書に無いキャラは、従来どおり「E ごとにCTを開始」（規則なし）。統合する 18 個（A）の窓の長さ・CTの有無は、gcsim ソースを読んで辞書に入れる（作業内容 1）。分からないものは「規則なし」とし、レポートに一覧で出す。
2. **実行後の書き戻し**（案B、フェーズ6の D20）
   - gcsim の結果で、E のアクションごとのCT（`cooldown`）を上書きする。CTが発生しなかった E（ステップなど）は `cooldown: 0` にする。辞書の規則より、gcsim の結果を優先する。

辞書は概算用（実行前のCT違反判定）で、書き戻し後は gcsim の実際の結果が使われる。

### UI・変換
- アクション構築の追加ボタン（`StintSequenceEditor.tsx`）: N は「N」の1つ、A の派生のボタンは無くなる。
- gcsim 変換（`actionMapping.ts`）: N は `attack`（段の連続チェックの警告は不要になる）、ニィロウの対応表（`CHARACTER_ACTION_OVERRIDES`）は削除する。
- DB管理のアクション編集: N と E の派生の編集項目を、新しい持ち方に合わせる。

### 既存の保存データ
- N1〜Nn・A の派生アクションの ID は使えなくなる。**旧データの移行はしない**（D13）。保存済みの編成・スロット・JSON は、作り直す前提。

## 作業内容

1. 規則辞書の調査と作成: 統合する A の 18 個について、gcsim ソースから「窓の長さ・窓の中の E のCTの有無」を読み取り、辞書（データファイル）に入れる。読み取れないものは「規則なし」とする。
1b. マスター生成器（`characterMasterGenerator.ts`）: N を1アクション（`_n`、段ごとの値付き）に、A の派生を生成しないように変更。レポートに、統合したアクションの一覧を出す。
2. 型（`ActionDefinition`）: 段ごとの値を持てるようにする。
3. マスターデータを再生成する（`npm run build:master`）。
4. 計算（`rotationCalculator.ts`）: N の段を自動で決めて所要時間を使う。規則辞書で、状態で切り替わった E のCTを判定する。
5. アクション構築 UI・記法・手順書・ガントチャート・DB管理を、新しい持ち方に合わせる。
6. gcsim 変換の対応表を更新する（N→`attack`、ニィロウの対応表を削除、段の連続チェックを削除）。
7. 型チェック・ビルド、ブラウザで確認（N を連続で追加して段ごとの所要時間、E の派生ボタンが出ないこと、ニィロウの編成、`/validate`）。

## 決定事項（D27, 2026-09-29）

- **CT**: 実行前の概算は「アクション状態の規則辞書」（案A）、実行後は gcsim の結果でCTを上書き（案B。CTが発生しなかった E は `cooldown: 0`）の**併用**。他の A のアクションにも、同じ形の辞書で対応する。
- **N の所要時間**: `duration` 未指定＝自動（段で決まる）、指定あり＝ユーザーの編集値。gcsim の結果は**編集済みでも最優先で上書き**する。
- **旅人(水) の `shortHold0Ticks`**: `Skill()` を読んで確認した。`hold=1`・`hold_ticks` のパラメータ指定なので **B（別ボタンのまま）**。B は 9 個のまま確定。

## 決定事項（D30, 2026-09-29）

- **窓の起点**: 窓を開く E の発動時刻（gcsim が状態を付ける時点と一致する）。
- **窓の中の E で上書きする値**: CT だけ（CTを開始しない）。効果バーも出さない。
- **静的な秒数で表せない状態**（爆発中・炎場・夜魂・近接姿勢など）: 「規則なし」として現状のまま（E ごとにCTを開始する扱い。実行後の書き戻しで補正）。規則なし: セノ・ライネ（爆発中）、ディシア（炎場）、タルタリヤ（近接姿勢）、ヴァレサ・キィニチ・マーヴィカ（夜魂）、藍硯 ほか。

## 実装した内容（2026-09-29）

- **辞書**: `src/data/actionStateRules.ts`。キャラ ID → { 窓の長さ, 使える回数, 根拠 }。8 キャラ分: ニィロウ（10秒）、キーティング（5.33秒・1回）、フレミネ（10秒・1回）、フリンズ（10.32秒・1回）、プルーネ（6.07秒・1回）、オデット（6.57秒・1回）、ドゥリン（6秒・1回）、ヴァルカ（12秒）。値は gcsim ソースの `skill.go` から（回数の上限は、消費する状態を削除する処理を確認できたものだけ 1回。ニィロウ・ヴァルカは未確認で制限なし）。
- **計算**: `rotationCalculator.ts` が辞書を使い、窓の中の E を「CTを開始しない・効果バーを出さない」扱いにする（計算時だけ付く `inStateWindow`）。編集画面では、窓の中の E に CT・効果の入力欄を出さない。
- **N**: マスターデータは `_n` 1つ（`normalHits`: 段ごとの所要時間・フレーム）。計算時に、連続した N の段を数えて段ごとの値を使う（最大段数で1段目に戻る）。所要時間を編集すると `durationManual: true` が付き、その値を優先する。gcsim の結果の書き戻し（フェーズ6）は、編集済みでも上書きする（D27）。
- **マスターデータ**: 生成器（`characterMasterGenerator.ts`）を変更して再生成した。アクションは 1,115 → 692 個。E の派生は B の 9 個（フィッシュル・早柚・綺良々・旅人(水)×4・マーヴィカ×2）だけ。N は 118 キャラで段ごとの値付き（残りはフレーム未実装のキャラ）。他のアクションに変更はなし。
- **DB**: `DATABASE_VERSION` を 13 に。旧バージョンの保存 DB は、マスターと入れ替わる（ロック・カスタムのキャラは保護される＝旧アクション ID のまま）。
- **gcsim 変換**: N → `attack`（段の連続チェックは廃止）、ニィロウの対応表を削除し、B の対応（`skill[recast=1]` など）を追加。E → `skill`。
- **UI**: 追加ボタンは「N」1つ。ヘルプの文言も更新。

## 所要時間の概算の改善（D31, 2026-09-29）

- **決定**: (1) 適用範囲は E・Q・CA・N・ダッシュすべて (2) 編集した所要時間だけ固定、他は自動（gcsim の書き戻しは編集済みでも上書き） (3) 窓の中の E のフレームは辞書に E ごとに持つ。
- **実装**: 計算（`rotationCalculator.ts`）が、アクションの所要時間を「次に続くアクション（出場の最後は交代）に対応するキャンセルフレーム（`frames.cancels`）」で決める（キーが無ければ全体のフレーム）。N は段ごとの表のフレーム、窓の中の E は辞書の `stageFrames`（ニィロウは E1〜E3 の 27 / 32 / 61 など。3段より後は最後の段の値）。フレームの無いアクション（ダッシュなど）は登録時の値。
- **結果**（「豊穣月開花」）: 1周が 18.75秒 → **17.77秒**（gcsim 実測 16.83秒）。ニィロウの E は 0.32 / 0.45 / 0.53 / 1.02 秒。アプリでも、2周目のニィロウのスキルCT違反（0.2秒残り）を検出できるようになった（gcsim の実測は約1.2秒待ち）。
- **残る差（約0.94秒）**: コロンビーナの重撃（露の状態で別モーションになる）など、状態で変わる動作。フェーズ6の書き戻しで合わせる。
- **注意**: 従来の保存済みの編成で、手で変えた所要時間（編集済みのフラグが無い）は、自動値になる（D13: 旧データは作り直す前提）。編集済みの値を「自動に戻す」操作は、まだ無い。

## 未確認・残っていること

- ニィロウの窓（pirouette）で、E・N を何回まで使えるか、E3 の後の状態は未確認（回数制限なしとしている）。

- ロック中のキャラは、旧アクション ID（`n1`〜）のまま残る。
