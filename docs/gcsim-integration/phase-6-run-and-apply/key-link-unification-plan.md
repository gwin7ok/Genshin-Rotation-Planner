# 効果キーの紐付けの保存先の統合（A: スキル・爆発 / B: それ以外）の検討

作成: 2026-10-09。決定 D63（「統合するかは、動いて使い方が分かってから決める」）の検討。**検討のみ（実装は未着手。選択肢を提示して決めてもらう）**。

## 1. 現状（2 本の流れ）

| | A: スキル・爆発 | B: 固有天賦・命ノ星座・武器・聖遺物・元素共鳴 |
|---|---|---|
| 紐付けの持ち主 | アクション定義 ID（例: `10000030-geo_e`） | 発動バフの定義 ID（例: `10000032-pyro_c2`、`wbuff_15502`） |
| 作り方 | gcsim を**実行**して集める（`probe:effects`・`link:effects`。gcsim のサーバーが要る）＋手で補う一覧 | gcsim のソースから作った辞書（`gcsim_key_catalog.json`）から**自動**（`buffGcsimLink.ts`。サーバー不要・マスター生成の最後に実行） |
| 保存先 | `public/data/action_effect_keys.json`（294 件）・`src/data/action_effect_links_by_duration.json`（150 件）＋**コードの表**（`actionEffectKeyOverrides.ts`・`actionEffectExtras.ts`・`actionEffectIncluded.ts`・`actionEffectApproved.ts`・`characterLinkedEffects.ts`） | マスターの各定義に直接（`gcsimKeys`・`gcsimCooldownKeys`・`gcsimExtraKeys`・`timing`・`gcsimTarget`・`gcsimNote`） |
| 実行時の読み方 | gcsim の結果を反映するとき、`action_effect_keys.json` をサーバーから**取得**（`fetchRuntimeData`）。コードの表は同梱 | マスターの定義を、そのまま使う（`getAvailableBuffsForCharacter`） |
| 「紐付けない」決定 | `effectKeyDecisions.ts`（レポート専用。画面は使わない） | `INTERNAL_INTERVAL_KEYS`・`IGNORED_KEYS`・`NATURE_EXCEPTIONS` など（生成と、レポートの両方が使う） |
| レポート | `effect_key_coverage.json` ＋ 同 `.md` | `master_effect_coverage.json` ＋ 同 `.md`（同じ形式: effects / targets / links / unlinked） |

**二重になっているもの**: 保存先（JSON と定義）・作り方（実行と辞書）・決定の置き場（3 か所）・レポート（2 本）。
**二重になっていないもの**: 辞書（`gcsim_key_catalog.json`）は 1 つで、A・B の両方が引く。レポートの形式はすでに同じ。

## 2. 統合すると何が良くなるか（例）

- **例 1: 鍾離のスキル**（`10000030-geo_e`）の岩柱のバー。いまは、`actionEffectKeyOverrides.ts` に `'construct:ZhongliSkill'` と書き、gcsim の結果の反映のときに、`action_effect_keys.json` と合わせて読む。統合後は、アクション定義に `gcsimEffect: { key: 'construct:ZhongliSkill', mode: 'expiry' }` を持ち、**画面・書き戻し・レポートが同じ定義を読む**。
- **例 2: 「gcsim 対象外」の印**。いまは、固有天賦・武器・聖遺物のボタンにだけ付く（B の `gcsimTarget`）。スキル・爆発（A）には、gcsim にキャラ自体が無い 9 キャラのアクションにも印が無い。統合後は、アクション定義にも `gcsimTarget` を持たせ、**同じ印を付けられる**。
- **例 3: 新キャラ・gcsim の更新**。いまは、`probe:effects` → `link:effects` → `link-buffs`（マスター生成）の 2 系統を、順番どおりに回す必要がある（`gcsim-サーバー更新手順.md` の注意: `link:effects` を 2 回回すと消える）。統合後は、「中間データ（実行結果）→ マスター生成」の 1 本の流れ。
- **例 4: レポート**。A と B で別々に見ている「未検討」「保留」を、1 本で見られる。

## 3. 統合しないとどうなるか

- 動作は、いまのままで問題ない（紐付けは両方とも 0 件未確認。画面の動きも揃っている）。
- 困るのは、**新しい種類のデータを足すとき**（例: アクションにも「gcsim 対象外」の印を付ける、アクションの CT のキーも持たせる）に、2 か所を直す必要があること。

## 4. 選択肢

### 案 1（推奨）: A の紐付けをマスターのアクション定義に持たせる（実行結果は中間データのまま）

流れ: **`probe:effects` → `link:effects`（gcsim を実行。中間データ `action_effect_keys.json` 等を作る。いまと同じ）→ マスター生成が、中間データ＋手で補う一覧を読んで、アクション定義に書き込む**（B の辞書 → 定義と同じ形）。

| 項目 | 内容 |
|---|---|
| アクション定義の追加項目 | `gcsimEffect`（キー・求め方・自分限定。いまの `primary`・`mode`・`self`）・`gcsimExtraEffects`（副次効果。いまの extras）・`gcsimIncludedKeys`・`gcsimLinkStatus`（`ok` / `no-bar` / `app-bar` / `not-in-gcsim`。いまの `status` と「紐付けない」決定） |
| 実行時 | `fetchRuntimeData('action_effect_keys.json')` をやめ、定義を読む。コードの表（overrides・extras など）は、マスター生成の入力になるだけで、実行時には要らない |
| 移行の安全策 | **等価確認の検査**（新しい経路と古い経路で、全 294 件のキー・求め方・副次効果が一致すること）を作ってから切り替える。`check:snapshots` は計算に触れないので影響なし |
| 影響を受けるもの | `applyGcsimResult.ts`（`ActionEffectKeyTable` の読み方）・`GcsimConfigDialog.tsx`・マスター生成（`build-character-master.ts` に、中間データの取り込みを足す）・`databaseService.ts`・型（`ActionDefinition`）・レポート 2 本の生成 |
| 規模の目安 | 中〜大（型の追加・生成・反映の 3 か所と、等価確認） |
| 長所 | 保存先が 1 つ。画面・書き戻し・レポートが同じ定義を読む。アクションにも「gcsim 対象外」の印を付けられる |
| 短所 | マスターの再生成が要る（DB バージョンを上げる）。中間データの更新（gcsim 更新時）は、いまどおり必要 |

### 案 2: 保存先は分けたまま、レポートと「決定」の置き場だけ統合する

- `effectKeyDecisions.ts` と B 側の決定の表を、1 つの決定表（キー → 理由）にまとめ、レポートも 1 本にする。実行時の読み方は変えない。
- 規模: 小〜中。長所: 影響が小さい。短所: 保存先（JSON とマスター定義）の二重は残る。

### 案 3: 統合しない（現状維持）

- 長所: 作業が要らない。短所: 新しいデータを足すたびに 2 か所を直す。

## 5. 推奨

**案 1**（段階 ① 新しい経路を作り、等価確認の検査を通す → ② 実行時を切り替える → ③ レポートを 1 本にまとめる）。理由: 保存先の二重が、**実際に困る**のは新しい種類のデータを足すときで、スキル・爆発の「gcsim 対象外」の印や、アクションの CT のキーの紐付けは、今後の候補に挙がっている。6-A2 が終わり、B の形（定義に直接持つ）が固まった今が、寄せやすい。

## 6. 確認したいこと

1. 統合する／しない（案 1・2・3）。
2. 案 1 のとき: **A の実行結果の中間データ（`action_effect_keys.json` など）を、いまのまま `public/data` に置く**（gcsim の更新時に作り直す。マスターに取り込む）でよいか。
3. 案 1 のとき: 段階 ③（レポートを 1 本にまとめる）も含めるか、後回しにするか。

## 7. 案 1 の問題点・デメリットの分析（2026-10-09）

| # | 問題 | 重さ | 内容（例） | 対策 |
|---|---|---|---|---|
| 1 | **ロック中・ユーザー作成のキャラに、古い（または無い）紐付けが残る** | 大 | DB の更新（バージョンが上がったとき）で、マスター由来のキャラは同梱の最新に置き換わるが、**ロック中・ユーザー作成のキャラは古いまま残る**（`mergeMasterWithProtected`）。いまは、スキル・爆発の紐付けを**実行時に、表（ID 引き）から取る**ので、ロック中のキャラでも最新の紐付けが効く。定義に持たせると、ロック中のキャラの紐付けが古いまま（gcsim 更新後も）になる | 紐付けの項目だけは、DB の更新のとき、ロック中のキャラにも**マスターの値で上書き**する（ID が同じアクションのみ）。ユーザー作成のキャラは、元から表に無いので影響なし |
| 2 | **gcsim の更新のたびに、DB の再登録が要る** | 中 | いまは、`action_effect_keys.json` を作り直して置くだけで、**既存の DB のまま**、新しい紐付けが効く（実行時に取得）。定義に持たせると、中間データを作り直した後、**マスターの再生成 → DB バージョンを上げる → ユーザーが再登録**が要る。B と同じ運用に揃うが、A 単独の更新が重くなる | 運用は B と同じ（`gcsim-サーバー更新手順.md` の手順に統合）。中間データの更新だけで済む軽い手段は、無くなる |
| 3 | **生成の順序が循環する** | 中 | スキル・爆発の紐付けを作る `probe:effects`・`link:effects` は、**マスターを読む**（アクション定義 ID・効果時間・命令の変換）。統合後は、紐付けを**マスターに書く**。新キャラのときは、「マスター生成（紐付け無し）→ 実行して中間データを作る → マスター生成を再度（取り込み）」の 2 回になる。`build:master` はネットワーク（genshin-db）が要る | **取り込みだけを行う軽い専用の手順**（`_relink` 相当。ネットワーク不要。今回の 6-A2 で実際に使った形）を、正式な `npm run link:actions` にする。手順書に順序を書く |
| 4 | **アプリ内の「最新マスターデータの動的生成」にも同じ取り込みが要る** | 中 | ブラウザ内の生成（`generateCharacterMaster`）も、B は辞書を実行時に取得して結び付けている。A も、中間データを実行時に取得して取り込む処理が、**スクリプトとブラウザの両方**で要る | 取り込みを**共通の純粋関数**（`buffGcsimLink.ts` と同じ作り）にして、両方から呼ぶ |
| 5 | **「同じ値が 2 か所」の再発（中間データとマスター）** | 中 | 中間データ（`public/data`）とマスターの定義に、同じキーが入る。**片方だけ更新する**と食い違う（例: 中間データを作り直したが、マスターを再生成していない）。メモリ「仕組みの統一」に反する形になりうる | 食い違いの検査（`gcsim:check` に、マスターの定義と中間データの一致を足す）。マスターに、どの gcsim のコミットから取り込んだかを記録する |
| 6 | **型・データの肥大** | 小 | `ActionDefinition` に項目が 4 つ増える（`gcsimEffect`・`gcsimExtraEffects`・`gcsimIncludedKeys`・`gcsimLinkStatus`）。キャラのマスターが約 70〜100KB 増える（1.37MB の 5〜7%）。全アクション 700 超に対し、項目を持つのは約 300 件 | 項目は「あるときだけ」書く。許容範囲 |
| 7 | **実行時の取得が無くなる利点と引き換えの、移行の手間** | 小 | `GcsimConfigDialog`・`applyGcsimResult` の読み方を変える。切り替えのとき、新旧の等価確認の検査を作らないと、書き戻しが黙ってずれる（`check:snapshots` は計算に触れないので、守ってくれない） | 等価確認の検査を、切り替えの**前に**作る（全 294 件のキー・求め方・副次効果・状態が一致） |
| 8 | **得るものが、当面は小さい** | 小〜中 | いまの画面の動きは変わらない。得られるのは、(a)「gcsim 対象外」の印をアクションにも付けられる (b) 保存先の一本化。(a) は、gcsim 未実装の 9 キャラのアクション 18 件が対象で、すでに「gcsim の計算ができない」旨の警告が出る | — |

### 縮小案（案 1-lite）

紐付けの**キーそのものは、いまのまま**（中間データ＋コードの表）にして、アクション定義には**「gcsim 対象外」の印と理由だけ**（`gcsimTarget`・`gcsimNote`）を、マスター生成で持たせる。問題 1〜5・7 が起きず、得られる (a) は得られる。保存先の一本化 (b) は得られない。

### 評価

- 問題 1・2・5 は、案 1 の**本質的な代償**（実行時に取るという柔軟さを失う）。対策はあるが、運用が重くなる。
- 得られる効果は、いまは (a) の「印」と (b) の一本化で、**緊急度は低い**。
- 推奨を見直す: **案 1-lite（印と理由だけを定義に持たせる）を先に行い、案 1（本体）は、アクションの CT のキーの紐付けなど、本当に必要になってから**。
