# 殺生桜（八重神子）のバーを、桜ごとに独立した 3 行で出す（実装計画）

作成: 2026-10-09。ユーザー依頼。**実装済み（2026-10-09。ユーザー決定: 推奨どおり・ラベルは「殺生桜 ①②③」）**。`TotemTracker` が行を割り当て（空きの一番上／最古の行）、`ActiveBuffSpan.lane`、`wrapTotems`（2 周目の再現・行の引き継ぎ）、`countDistinctActiveBuffs` と `organizeBuffsIntoRows` を行ごとに。スナップショット 75 並び（桜 6 並びが `L0〜L2` の差・持ち越し 2 並びを追加）、内蔵ブラウザで確認（3 行・4 つ目が行 ① を置き換え・持ち越しが行を引き継ぐ・バフ重複 1→2→3）。

## 1. 仕様（ユーザー依頼）

- 殺生桜のバーが、同じ行に重なって見える。**桜ごとに独立した計 3 行**で出す。
- 重複バフ（バフ重複の行）の数え方も、**行ごとに 1 カウント**（桜 3 つ = 3）。
- スキルで新しい桜を置くとき: 桜が **2 つ以下**なら、**バーがない一番上の行**に置く。桜が **3 つ**あるなら、ゲームの仕様どおり、**一番古い桜のバーを置き換える**（その行で、古いバーが終わり、新しいバーが始まる）。

## 2. 分析（問題が生じないか）

| # | 論点 | 結論 |
|---|---|---|
| 1 | 桜の数え方は、すでにあるか | **ある**。`totemTracker.ts` の `TotemTracker` が、gcsim と同じ数え方（上限 3・4 つ目で最古が消える・爆発で全部壊れる〔論示未達成〕）で持つ。効果バー用（`barTotems`）と CT の判定用（`totems`）の 2 か所で使う。バーは、押し出し・爆発で、すでにその時刻で切っている（`cutBar`） |
| 2 | 行の決め方（仕様どおり）は、数え方と矛盾しないか | 矛盾しない。`spawn` で、(a) 3 つ未満 → 生きている桜が使っていない行のうち**一番上**（番号が小さい行）、(b) 3 つ → 押し出される最古の桜の行をそのまま使う。同じ行で、古いバーが終わる時刻 = 新しいバーが始まる時刻になる。寿命で先に消えた桜の行は空くので、次は上の空き行が使われる |
| 3 | 3 行を超えることはあるか | ない（上限 3）。論示の有無で寿命が変わっても同じ。上限は、マスターの `spawnsTotem.max` を使う（行数 = max） |
| 4 | バフ重複の数え方 | いまは、同じアクション由来（`buffId` が同じ）を 1 つと数える（`countDistinctActiveBuffs`）。**行（lane）つきのバーは、`buffId` + 行で数える**ように変える。桜 3 つ = 3。他のバフ（行を持たないもの）は変わらない。数えるのは桜だけで、他に影響しない |
| 5 | 画面の行 | `organizeBuffsIntoRows` が `buffId` ごとに 1 行にしている。**行つきのバーは、行ごとに別の行**にする（`GanttChart.tsx`。ラベル列・バー領域は同じ配列から作っているので、ずれない）。ラベルは「殺生桜 ①②③」の形（行の番号つき）。桜が 1 つしか出ない編成は、行が 1 本のまま |
| 6 | 2 周目の折り返し（持ち越し） | **一番手間がかかる所**。持ち越しバー（1 周目の終わりに残る桜）は、いまは、ループ先頭で同じ効果の次の開始があればそこで切る（桜が複数あっても、最初の 1 つ目の新しい桜で全部切れる = 不正確）。行を持たせるので、**2 周目の動きを再現**する: 1 周目の終わりに残る桜を初期状態にした `TotemTracker` で、ループの区間の桜の設置を順に流し、(a) 置き換えられた持ち越しの桜は、その時刻で切る、(b) **置き換えた新しい桜のバーの行を、持ち越しバーの行にする**（行の引き継ぎ。同じ行で、持ち越しバーが終わる時刻 = 新しいバーが始まる時刻）、(c) 置き換えられずに寿命で終わる桜は、新しいバーが使っていない行に置く（行が全部埋まるときは、元の行）。これで、同じ行に、重なって見えることが（ほぼ）なくなる |
| 7 | 他に行を持つバーはあるか | **ない**（`stackable` = 同時に複数ある設置物は、いまは殺生桜だけ）。他の設置物が増えたときも、同じ仕組み（`TotemTracker` の行）でできる |
| 8 | スナップショット | 八重神子の並び（約 8 件）の、効果バー（`lane`）と、バフ重複の数が変わる。**それ以外は変わらない**はず。差を説明してから保存する |
| 9 | gcsim との整合 | 桜のバーは、アプリの計算だけで決まる（gcsim の反映では、桜の継続時間を書き戻さない。D81）。行の追加は、gcsim の設定文・結果の反映に影響しない |
| 10 | 画面の高さ | 八重神子の出場ブロックが、最大 2 行ぶん（桜 3 行 − 1 行）高くなる（桜が同時に 2〜3 つ出る編成のときだけ。行は、バーが 1 本でもあれば出る） |

**結論: 問題なし。実装できる。** 手間があるのは、持ち越し（§2-6）だけ。

## 3. 実装計画

### 段階 A: 行の割り当て（`totemTracker.ts`・`rotationCalculator.ts`）

| # | 内容 |
|---|---|
| A1 | `Totem` に `lane`（0 始まり）を足す。`spawn` が、(a) 押し出しがあれば押し出された桜の行、(b) なければ、生きている桜が使っていない一番小さい行 を割り当てる。戻り値に `lane` を含める（`{ popped, lane }`）。CT の判定側（`totems`）は戻り値を使わないので、挙動は変わらない |
| A2 | `ActiveBuffSpan.lane?: number` を足す。バーを作る箇所（`rotationCalculator.ts` 約 995 行）で、`effectSpan.lane = lane` |
| A3 | 持ち越し（`carryOverBuffs`）: 1 周目の終わりに生きている桜（`TotemTracker` の状態）を初期状態にして、ループ先頭以降の設置（開始時刻がループ先頭以降の桜のバー）を時刻順に流す。置き換えられた持ち越しの桜は、その時刻で切り、置き換えた桜の行を持ち越しバーの行にする。置き換えられない桜は、空いている行へ。`wrapEffect` の「同じ効果の最初の開始で切る」処理は、行つきのバーでは使わない |
| A4 | `countDistinctActiveBuffs`: キーを `buffId`（行つきのバーは `buffId#行`）にする。名前の一覧も同じキーで |

### 段階 B: 画面（`GanttChart.tsx`）

| # | 内容 |
|---|---|
| B1 | `organizeBuffsIntoRows`: キーを `buffId`（行つきのバーは `buffId#行`）にして、行ごとに別の行にする。並びは、同じ `buffId` の行を、行の番号順に |
| B2 | ラベル: 行つきの行は、名前の後ろに「①②③」を付ける。ツールチップのバーに「行 N」 |

### 段階 C: 確認・記録

- スナップショットに、桜のバーの `lane` を足す（行つきのバーがあるときだけ）。八重神子の並び（E ×3・E ×4 で押し出し・爆発〔論示あり／なし〕）で、行が (0,1,2)・(0,1,2,0)・爆発で全部切れる、になることを確認。持ち越しの並び（ループあり）も追加。
- バフ重複の数（桜 3 つで 3）。
- 内蔵ブラウザで、八重神子の E ×4 の並びを確認（4 つ目が最古の行を置き換える）。ループ先頭の持ち越しの桜が、行を引き継ぐ。
- 決定ログ・次のセッション用プロンプトを更新。
