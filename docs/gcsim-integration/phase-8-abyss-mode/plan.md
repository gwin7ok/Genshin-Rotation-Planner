状態: **計画確定（2026-11-19）。段階 1・段階 2 を実装済み（ブランチ `feat/abyss-mode`）。段階 3 以降は未着手**。確認事項はユーザーに 1 問ずつ確認し、すべて決定した（残りは Q4b だけ。段階 4 の着手時に確認する）。

## 目的
元素チャージ効率（ER）の計算（フェーズ7）と DPS 計算を、**幽境（HoYoLAB の `hard_challenge`。表記は「幽境の危戦」。Game8 は「幽境の激戦」と書いており、どちらが公式か未確認）の戦闘**に合わせられるようにする。

issue #54 の本文: 「元素チャージ 0 スタート、ダメージ無効時間の設定等」。2026-11-19 にユーザーが足した観点:
1. 特定の時間に粒子が発生することがある。どう設定するか。
2. 戦闘後であれば、実際に戦った敵を設定できるか。
3. 幽境専用の機能として、何を実装すると便利か。

**目的の中心は ER 計算**。「1 周目だけ（初動）＋ 2 周目以降も繰り返す（ループ）アクションのローテーションで、爆発のエネルギーがきちんと貯まった上で、繰り返しに設定した場所の爆発が毎回撃てるか」を確認すること。まず元素チャージ効率計算の部分を中心に実装し、**DPS 計算への対応は「おまけ」**（後の段階）。

## アプリ全体のモード切り替え（ユーザー指示 2026-11-19）
「アプリ全体で、幽境モードと通常モードを切り替えられるようにする」。

- **通常モード**: 従来どおり（開始エネルギー満タン・敵の周期の粒子・敵 1 体の既定。ダメージ無効なし）。**出力は今と変えない**（`check:snapshots` で確認）。

- モードは 1 つのアプリ全体の設定で、ER 計算・DPS 計算・ガントチャートの表示（無効時間の帯）が同じモードを使う（Q1 の「共通にする」と同じ方向）。
- 通常モードと幽境モードで、**それぞれの条件の値を別に保存**する（切り替えても、もう片方の値を失わない）案。確認事項 Q8・Q9 で決める。
- 影響: 保存キーを `SETTING_KEYS` に足す（バックアップに入る）／画面の入口／使い方ガイド／ja・en の文言。

## 現状（コードの事実）
- 敵の粒子は、`buildGcsimConfig` の `enemyParticles`（`energy every`）。ER ダイアログと DPS ダイアログが、**それぞれ別に値を持つ**（`EnergyRechargeDialog.tsx` の `pMin` ほか、`appSettings.ts` の `DpsSettings.particles`）。
- 敵は `EnemySetting`（レベル・耐性）。DPS ダイアログだけで設定できる。ER ダイアログは、敵 1 体の既定のまま。
- 開始エネルギーは常に満タン。ER の判定（`passCount`）は、最初の爆発を「初期満タンで撃てる」として数えない。
- ER の判定は、ローテーションを `ER_LOOP_ITERATIONS`（4）周回し、全周で成功する値（確実）などを求める。戦闘時間（秒）の概念は無い。
- 敵から受けるダメージ（`hurt`）は、ディシアの効果などのため。ダメージ無効とは別。

## 段階 1 の実装メモ（設計上の注意。実装の着手時に、この内容を前提に詳細を詰める）

1. **開始エネルギー 0 の渡し方**: キャラ行に `+params=[start_energy=0]`。`buildGcsimConfig.ts` の `paramList`（ヘクセレイ・諭示・旅人の真月）に足す（既存の `+params=[...]` と 1 つにまとめる）。指定なし（満タン）の出力は変えない。
2. **集計の実行が全種で外れる危険**（最重要）: `computeRequiredEr` の集計の段階は、「基準（`ignore_burst_energy=true`）と爆発の並びが一致する種だけ」を使う。0 スタートでは、全員の ER を +1000% にしても、最初の爆発が粒子の足りない分だけ遅れ、**全種が不一致で外れて `errorMismatch` になりうる**。→ 一致の判定に、最初の爆発の待ち許容（Q2b）を使う（`firstMismatchChar` は、すでに遅れの許容 `delayFrames` と立ち上がりの窓 `warmupWindows` を持つ）。着手時に、実測で確かめる。
3. **爆発待ちで行動リストが止まる**: 0 スタートで、最初の爆発の前に E が無く、敵の粒子も 0 のとき、エネルギーが貯まらず最後まで止まる。止まったまま終わった種は「届かない」として扱う。
4. **`passCount` の変更**: 初期エネルギーを 0（`tl.max` ではなく）にし、最初の爆発も数える。最初の爆発の待ち許容は、最初の爆発にだけ使う（2 回目以降は従来の `delayFrames`）。開始が満タンのときの判定は変えない。
5. **時刻指定の粒子**: 「戦闘開始からの秒」→ フレーム（`round(秒 × 60)`）→ `energy once interval=<フレーム> amount=<個数>;`（複数行）。amount は整数。1 個 = ER 100% で 2 エネルギー（出場中。控えは gcsim が減らして計算する）。
6. **戦闘時間と周数**: 幽境モードでは、戦闘時間（秒）から周数を自動で決める（ローテーションの長さから。初動 + ループ × 周数 ≧ 戦闘時間）。通常モードは従来の `ER_LOOP_ITERATIONS`。**ローテーションの長さが見積りで、実行では遅れで伸びる**ことに注意（`buildGcsimConfig` の `duration` の余裕と同じ扱い）。
7. **保存**: モードごとに、条件の値と ER の結果を別のキーで保存（`SETTING_KEYS` に足す。`check:backup`）。結果の指紋は、設定文のハッシュなので、モードや条件が変わると「編成が変わっています」と出る（今の仕組みのまま）。
8. **フェーズ7 の記録の訂正**: [../phase-7-required-er/plan.md](../phase-7-required-er/plan.md) の調査結果 2 は、`+params=[start_energy=0]` の形では効く、と注記した。

## 段階 1 の実装結果（2026-11-19）
実装メモ（上）のとおりに実装した。実装で決めたこと・分かったことは、[全体の決定ログ D365](../progress.md) にある。要点:

- **リスク（集計の実行が全種外れる）は、実測で確認した**。0 スタートの集計の実行（ER +1000%）は、最初の爆発が基準より遅れ（ベネット + 香菱: 0.75〜3.9 秒）、以降も同じだけずれる。許容 0 だと全種が不一致になる。→ 幽境モードの集計では、爆発の並びと「最初の爆発以降の相対的な遅れ」だけを見て（`firstMismatchChar` の `firstDelayFrames = Infinity`）、最初の爆発の待ち許容は窓の集計（`passCount`）で判定する。許容に届かない爆発は、ER をいくら上げても足りない = 「届かない」。
- **最初の爆発は、計画の時刻から測る**。基準の実行の爆発のフレーム（`plannedBurstFrames`）を、集計のタイムラインの爆発に付け（`withPlannedFrames`）、`limit = 計画 + 最初の爆発の待ち許容` までの粒子で判定する。検証（実機の実行）も、同じく計画との差で見る（`firstMismatchChar` の `firstDelayFrames`）。
- **既定値**: 戦闘時間 180 秒・最初の爆発の待ち許容 **0.5 秒**（最初は 10 秒にしていたが、幽境の想定の形 = 初動（1 周目だけ）をスキルだけで回して爆発のエネルギーを貯める形で測り直し、変更した。ユーザーの編成（八重神子・オデット・サンドローネ・七七）は、ER +1000% で最初の爆発の遅れが 0.0 秒。10 秒だと七七の安定が 85.3%、0.5 秒だと 137.8% で、10 秒は足りなさを隠す。初動の中で爆発を撃つ形（プリセット 5 編成。ER +1000% でも 0.7〜7.2 秒遅れる）は、0.5 秒だと「届かない」になるので、画面で秒数を増やす）。
- **戦闘時間 → 周数**: ローテーションの見積りの長さから、初動 + ループ × 周数 ≧ 戦闘時間 になる周数（1〜30）。シミュレーション時間は従来の余裕（見積り × 1.3 + 10 秒）のまま。
- **DPS ダイアログ**: 幽境モードのときは、「まだ幽境の条件に対応していない（通常モードと同じ条件で計算する）」と知らせる。計算は変えない（段階 4）。
- **指紋**: 結果の指紋は、編成・ローテーションだけの設定文（幽境の条件は含めない）。条件は、結果に記録し、いまの入力と違うときは警告する（`er.abyssConditionChanged`）。
- **画面の確認**: 内蔵ブラウザで確認済み（切り替え・保存・入力欄・プリセット 1 編成の算出）。
