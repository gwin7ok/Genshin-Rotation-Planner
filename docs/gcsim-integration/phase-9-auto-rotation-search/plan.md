# フェーズ9: ローテーションの自動探索（構想・第 1 歩）

作成: 2026-11-20 / 状態: 進行中（第 1 歩の測定ができた）

## 構想（ユーザーとの相談で決めた方向）
アクションが空の状態から、DPS が高いローテーションを探す。探索の範囲を絞るため、次の形にする。
1. アプリ内で、CT 違反が起きない候補だけを作る（`cooldownCheck.ts`・`violations.ts` を制約に流用）。
2. キャラの性能から、アタッカー（DPS の高いキャラ）を決め、その出場時間にバフ・デバフを重ねる。
3. 候補をアプリ内の簡易スコアで数十件に絞り、gcsim に渡して検証する（gcsim は「探す道具」ではなく「確かめる道具」）。

## 第 1 歩: 単独 DPS の測定
- `npm run probe:solo-dps`（`scripts/solo-dps.ts`）。各キャラを 1 人だけで E → Q → 通常攻撃×4 の繰り返しで 30 秒回し、DPS を出す。装備は「仮値を使う」と同じ。
- 2026-11-20 の結果（20 回）: 上位は 神里綾華 17162・フリンズ 14482・エスコフィエ 13246・ナヴィア 11833・凝光 11624。下位は サポート（バーバラ 99・ミカ 323・ナヒーダ 415）。
- **分かった問題**: 固定のローテーションでは、胡桃（3547）・魈（3572）など、通常攻撃以外（重撃・落下）が主力のキャラが過小評価される。アタッカーの判定には、キャラごとに数種類のローテーションを試して、最大を採る必要がある。
- 単独では反応が起きないので、反応が主力のキャラ（ナヒーダ・ニィロウなど）は低く出る。「アタッカーか」の判定の材料にはなるが、編成での価値は測れない。

## 第 1 歩の続き: 複数ローテーション（2026-11-20）
- 7 種（通常攻撃・通常攻撃長め・通常+重撃・重撃のみ・落下・高落下・長押し E）を試し、最大を採る（10 回）。胡桃 3547→5779（通常+重撃）、魈 3572→6601（高落下）、ヌヴィレット 5034→29322（重撃のみ。1 位に）。
- 最適な型は、通常攻撃長め 71・重撃のみ 26・通常+重撃 18・長押し E 10・高落下 2 キャラ。型で DPS が数倍変わるので、アタッカー判定に複数ローテーションは必須。
- 落下は、gcsim が低空落下を許さないキャラでエラーになる（胡桃など）。重撃のみは、攻撃直後でないと重撃できないキャラ（ニィロウなど）で失敗する。失敗した型は飛ばす。

- 所要時間: gcsim 3 回で 1 候補あたり 0.35〜0.7 秒。150 個で 50〜115 秒、10 個の 10 回で 15〜27 秒。1 回の探索は、2〜3 分。

## 2026-11-20 手組みとの差の調査と改善

編成: 八重神子・オデット（仮値）・サンドローネ・七七（持ちキャラの装備）。手組み（`scripts/probe-rotation.ts` で、探索と同じ条件の戦闘 120 秒・10 回）は **193.5k**。

- 手組みの 1 周だけを繰り返しても 194.9k → 開始の 1 周と定常ループを分ける構造は、主因ではない。
- 効いたのは Q の使い方: サンドローネは `E C E Q C E`（途中で Q）で 196.8k、Q が先頭だと 167k。八重神子・オデットの Q は使わない方が速い（八重神子に Q を足すと 184.6k）。七七の Q は有無・順序とも影響なし。
- 改善: ① 全員に「Q を使わない」を足す ② アタッカーの Q の位置（先頭・末尾・E の直後・重撃の直前）③ 末尾の E ④ 繰り返し回数は 1〜目安+1（上限 5）⑤ gcsim が実行できない候補（サンドローネは E なしの `通常 重撃` で decode エラー）は後続で補う ⑥ **近傍探索**（gcsim で良かった上位 5 件から、1 人の中身だけ / 出場の順番だけが違う候補を試す。予算 150）。
- 結果: 51k → 124k（40 秒）→ 143k（120 秒）→ 167.5k（Q の位置など）→ **185.1k**（近傍探索。手組みの 96%）。
- 残る課題: 所要時間 860 秒（遅い）／簡易スコアと DPS の順位相関 0.33（バフの重なりの採点が合っていない。手組み相当の候補が簡易スコア 3460 位だった）／サンドローネの重撃 decode エラー（E なしの重撃）。

## 2026-11-20（続き）手組みと同等以上の DPS を見つける方法の確立

結論: **簡易スコアで絞って gcsim で確かめる方式は、順位相関が 0.2〜0.3 で当てにならない。gcsim の結果を使った山登り（近傍探索）で、手組みを超えた。**

- 実測（八重神子・オデット・サンドローネ・七七、戦闘 120 秒・10 回）: 手組み **193.5k** → 山登りを組み込んだ探索の 1 位 **200.1k**（`七七[E] → 八重神子[E×3] → オデット[E spE] → サンドローネ[C E Q C]`、長さ 17.3 秒）。
- 山登り: gcsim の結果が良い上位 2 つから、1 か所だけ変えた候補を全部試し、良くなったらそこへ移る。近傍 = 出場の入れ替え・動作の消去・移動・差し込み（e / q / ca / n / e_recast）。`neighborsOf`（candidates.ts）。
- 重なり採点を「効果ごとの和集合」にする案は、順位相関が -0.08 に落ち、結果も悪化したので戻した。出場の順番をサポーター → サブの固定にしない自由な並べ替えも、候補が 24 万個に増えるので列挙をやめ、近傍（隣との入れ替え）に任せた。
- 探索中の戦闘時間は最大 60 秒（3 回）、最後の確認だけ指定の戦闘時間（10 回）。60 秒・3 回の値は、勝ち残った候補に偶然の良さが混じる（山登りの最終 196.4k が、120 秒・10 回では 186.9k）ので、最後に上位 8 件を確かめ直す。
- バグ修正: 山登りで見つけた候補が、最後の確認の対象から漏れていた。
- 残る課題: 所要時間 約 20 分（速度の改善が要る）／サンドローネの重撃の decode エラーで gcsim に落ちる候補がある（E なしの `通常 重撃`）。

## 2026-11-20（続き）速度改善

- **原因: Node 側の gcsim 呼び出し（scripts/gcsim-node.ts）で、同時に呼んだ要求が全部同じ Worker に割り当たり、実質ずっと直列だった**（Worker を選んでから仕事を数えるまでの間に await があり、全員が「空き」と見ていた）。Worker を同期で選ぶように直し、1 回あたり 2000ms → 115〜160ms（24 Worker）。ブラウザ側（gcsimWasm.ts）は同期で選んでいるので、この問題はなかった。
- 山登りに、近傍ごとの「先に 1 回だけ回して悪いものを落とす」足切り（最良の 85% 未満）を追加。
- 結果: 同じ設定の探索が 1032 秒 → **182 秒**、1 位は同じ 200.1k。
- 探索中の戦闘時間を 40 秒にする・近傍を 45 に絞る案は、山登りが局所解で止まり DPS が落ちた（183.8k）ので、やめた（探索中は 60 秒、近傍 70）。
- 速度の測定は、`GCSIM_NODE_WORKERS=24 npm run probe:search …`（スクリプトの既定は コア数 − 4、最大 24）。

## 2026-11-20（続き）持ちキャラ編成（ナヒーダ・ニィロウ・コロンビーナ・ラウマ）

- 手組み = 149.5k（60 秒）。探索は 107〜128k までで、同等には未到達（コロンビーナをアタッカーに固定しても 115〜128k）。
- 効いている要素（アブレーション）: ニィロウ E×4（153.7k → E×1 は 106.2k）、ラウマの長押し E、コロンビーナの重撃×3〜5。どれも「全部そろって初めて効く」形で、1 手ずつの山登りでは届かない。
- 対応: E の連続回数をマスターデータ（`mode.repress`）から導いて出発点に入れた。CT 違反を数個まで許容。山登りはアタッカー組ごと。E を含む型の繰り返しは E の CT で抑える。
- 未解決: 簡易スコアと gcsim の相関が 0.3 前後。コロンビーナ・アタッカー組の出発点が弱く、山登りで伸びない。次の案: マスターデータの「条件つき効果」（followUps・extraEffects）から、効果を起こす並び（E×4・E→N×3 など）を部品として組み合わせて出発点を作る。

## 2026-11-20（続き 2）持ちキャラ編成で手組みの 95% に到達

- 分かったこと: 手組み（149.5k）は **周回の開始位置 = 1**（先頭の「コロンビーナ [N]」は 1 回目だけ）。探索は常に開始位置 0 だったので届かなかった。さらに、ラウマの Q を足す・開始位置を 1 にする、のどちらか片方だけだと下がる（120k → 117k / 107k）、両方で 145k。1 手ずつの山登りでは届かない形。

| フリーナ | 63.2k | 64.5k・1255 秒 | 64.4k（手組みは評価で落ちた） | 探索できず（NO_VALID_CANDIDATES） |

- 読み取り: 良い出発点があると、手組みを超える（+3〜+11%）うえ、時間が 2〜12 分の 1。出発点の質が、探索の質と時間を決める。辞書で作る候補が、手組み並みの質なら、効果が大きい。
- 「手組み + 総当たり」は、「手組みだけ」より劣る（月開花 177.4k < 184.2k）。総当たりの割り当てが増えて、山登りの予算が薄まるため。良い出発点があるときは、その割り当てに予算を集中させる設計が要る。
- 手組みの評価での扱い: フリーナは、CT 違反などで候補の評価に通らなかった（CT 違反が 4 件を超える、または CT 以外の警告）。辞書で作る候補は、評価に通る形で作る。
- 重撃の前に通常攻撃が要る規則（`CHARGE_REQUIRES_ATTACK`）で、測定の枠を使った後に落ちる候補が多い（月開花 約 80 個）。近傍の生成か評価で、事前に除くと、枠を無駄にしない。

## 段階 1: 先置き型の分割と、重撃の事前チェック（2026-11-21）

- 追加: ①重撃の直前が通常攻撃でない並びを、gcsim に渡す前に除く（`evaluate.ts` の `chargeViolation`）。②アタッカーのスキル・爆発の出場を、他のキャラの前・間に置く「先置き型」の初期候補。③先置き型（同じキャラが、間に別のキャラを挟んで 2 回出る形）を、出発点の選び方で別の使い方として数える（簡易スコアが低くて上位 400 に入らないため）。
- 結果（同じ条件の 1 位・所要時間。基準 → 段階 1）: 月開花 164.7k・686 秒 → 164.7k・687 秒 / フリーナ 64.5k・1255 秒 → 65.1k・385 秒 / 雷電 47.1k・946 秒 → 47.1k・321 秒 / 刻晴 49.8k・882 秒 → 52.5k・344 秒。時間の短縮は、①と、worker 数の修正（前の項）による。
- 月開花の先置き型: 718 個が評価を通ったが、簡易スコアの順位は 748 位以下だった。③で出発点に入れても、1 位は変わらなかった。手組みの 184k は、ニィロウ E×4・ラウマ hE Q・コロンビーナ Q と先置き・重撃 ×5 が全部そろって初めて出る。1 手ずつの山登りでは、先置き型の出発点からも届かない。
- 学び: 形を「作る」だけでなく、各部品（キャラごとの使い方）を、そろえた形で作る必要がある。これは辞書（運用型 = 使う動作の組）の役割で、段階 2 で扱う。

## 段階 2: 知識辞書（月開花の 4 キャラ）を出発点にした探索（2026-11-21）

- 実装: 辞書の型・本体（`src/masterdata/knowledge/`）、書き出し（`npm run build:knowledge` → `public/knowledge/`。`check:knowledge` で古さを検査）、取得（`src/utils/knowledge/source.ts` の `KnowledgeSource`。探索ダイアログが、編成のキャラの分だけ取得）、出発点の組み立て（`rotationSearch/knowledgeSeeds.ts`）。辞書が無い・取得できないときは、従来の探索。
- 辞書の中身: コロンビーナ（先置きの E・Q + 最後の重撃 4〜6 回 + 周回前の通常攻撃）、ナヒーダ（E・Q）、ニィロウ（E×4）、ラウマ（長押し E・Q）。slot（出場の順番）と運用型の組み合わせから、全部そろえた形を作る。
- 結果（月開花・画面と同じ条件・同じ設定）: 1 位 **184.3 ±3.0k**（辞書なし 164.7k → +11.9%。手組み 174.6k を +5.6% 上回る。手組みから登った場合の 184.2k と同等）。所要時間は 688 秒（辞書なしの 687 秒と同じ）。`ニィロウ[E×4] → コロンビーナ[E Q] → ナヒーダ[tE Q] → ラウマ[hE Q] → コロンビーナ[C N C J C×2]`。
- 学び: 辞書で「そろえた形」を出発点に入れれば、手組みを渡さなくても、手組み超えに届く。時間は、辞書で作った出発点に予算を集中させれば、減らせる見込み（段階 0: 手組みだけからだと 336 秒）。
