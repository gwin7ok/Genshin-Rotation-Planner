# ローテーション探索の「知識辞書」の設計（2026-11-21。検討中）

目的: 原神の知識（運用型・順序の制約・コンボ）を辞書にして、gcsim に投げる前の候補を、理屈で少数だけ作る。
探索（総当たり + 山登り）の置き換えではなく、**出発点を足すもの**（段階 0 の測定で、効果の上限を確かめてから進める）。

## 前提（ユーザー指示 2026-11-21）

- 辞書は、**サーバー側で保持し、必要になったらクライアントに渡す**。アプリの本体（JS）には入れない。
- 現在の公開先は GitHub Pages（静的）。「サーバー」は、当面は同じ配信元の静的ファイル（`public/knowledge/`）。別のサーバーに移しても、クライアントの呼び出し口は変えない。

## 構成

```
public/knowledge/
  index.json              … 版・キャラ ID → ファイルの対応・ハッシュ
  chars/<キャラID>-<英語名>.json   … キャラ 1 人分（例: 10000046-pyro-hu-tao.json。画面は index.json の対応から読む）（運用型・コンボ・制約）
  rules.json              … 編成をまたぐ規則（下記）
```

- **分割の単位はキャラ 1 人**。編成の 4 人分だけ取りに行く（全キャラで数百 KB を超える見込みなので、まとめて渡さない）。
- 取得は、探索を始めるときだけ（`fetchKnowledge(characterIds)`）。結果は、版つきでメモリ + IndexedDB に置く（`persistence.ts` の規則に従う）。オフラインなら、辞書なしで従来の探索（総当たり）に戻る（辞書は、必須ではなく加算）。
- クライアントの口は 1 つ: `KnowledgeSource { load(ids): Promise<KnowledgeBundle> }`。実装は `StaticFileSource`（今）と、将来の `ApiSource`。
- 版: `index.json.version` が、辞書の版。gcsim の版（`gcsim.config.json`）と対応づけて持つ。合わない辞書は使わない（`gcsim:check` で検査）。
- 生成物ではなく**手で保守するデータ**なので、元は `src/masterdata/knowledge/`（型つき TS）に置き、ビルドで `public/knowledge/` に書き出す（`npm run build:knowledge`）。型検査・ID の存在検査・gcsim の実測による裏付けの検査を、ここで行う。

## キャラ 1 人分の中身（案）

```ts
interface CharacterKnowledge {
  characterId: string;                 // ID（名前ではなく）
  archetypes: Archetype[];             // 運用型（編成の条件つき）
  combos: string[][];                  // 実戦のコンボ（FILL_TEMPLATES の代わり。例: ['n','n','n','ca','dash']）
  macros: string[][];                  // ひとまとまりの並び（sequenceRules の MACROS を移す）
  prerequisites: Prerequisite[];       // 前提（sequenceRules の PREREQUISITES を移す）
  orderHints: OrderHint[];             // 順序の制約（下記）
  evidence: Evidence[];                // 根拠: gcsim の実測（編成・条件・DPS）か、出典の要約（文章の転載はしない）
}
interface Archetype {
  name: string;
  when?: Condition;                    // 編成の条件（例: 草露を作れる水・草がいる）
  role: 'attacker' | 'subAttacker' | 'supporter';
  split?: 'setupFirst';                // 設置・爆発の出場を先に、ダメージの出場を最後に分ける（サンドイッチ型）
  use: string[];                       // 使う動作（e / e_hold / q …）。E の回数（例: E×4）も
  fill?: string[];                     // ダメージの出場の型
}
type OrderHint =
  | { kind: 'before'; target: 'attacker' | string }   // 例: バフ役は、アタッカーの前
  | { kind: 'snapshot' }                              // スナップショット。バフの後に置く
  | { kind: 'last' } | { kind: 'first' };
```

- 順序の制約のうち、**既存データから導けるもの**（効果の長さ・対象・スナップショット）は、辞書に書かない（アプリが導く）。辞書は、導けないものだけ（運用型・コンボ・元素付着の順序・競合）。
- 出典（Wiki など）の文章は転載しない。事実を自分の言葉で書き、実測（gcsim）で裏付ける。裏付けのない項目には、`evidence` が空であることを示す印を付け、探索では「確かな出発点」としては使わない。

## 探索での使い方

1. 編成の 4 人の辞書を取得する（`KnowledgeSource.load`）。
2. 運用型を、編成の条件で絞る → 役割の割り当てと、各キャラの使い方が数通りに絞れる。
3. 順序の制約（辞書 + 既存データから導いたもの）で、出場の並びを組む（制約を満たす並びだけを列挙）。分割型（サンドイッチ）も、ここで作る。
4. 作った少数の候補（約 20〜50）を、探索の**出発点に必ず入れる**（`extraSeeds`）。総当たりの候補も従来どおり作る。
5. 山登りは従来どおり（辞書で作った出発点が良ければ、予算を減らせるかを段階 0 で測る）。

## 段階

- 段階 0: 手組みを出発点にして、探索の効果と時間の上限を測る（`--seed-hand` / `--seeds-only`。結果は plan.md）。
- 段階 1: 既存データから、順序の制約と分割型を導く（辞書なし）。月開花の先置き分割型。
- 段階 2: 辞書（手組みのある編成のキャラ 約 15 体）と `KnowledgeSource`・`build:knowledge`。
- 段階 3: 辞書を広げる（下書きは LLM、実測で検証）。

## 決めること

- 辞書の置き場の最終形（静的ファイルのままか、API か）。
- 辞書の保守の担当と、新キャラ追加時の手順（`docs/ゲーム新キャラの取り込み手順.md` に足す）。
- 利用者の持ちキャラの装備を辞書の条件に使うか（例: 熟知が高ければ別の運用型）。

## 続きの出場（then。2026-11-22・段階 A）

1 回の出場に収まらない形（同じキャラが、間に別のキャラを挟んで 2 回以上出る）を書くため、運用型に `then`（続きの出場 `{ slot, use }` の並び）を足した。
- 出発点の組み立て（knowledgeSeeds）は、`use` と `then` を、それぞれ 1 つの出場（slot つき）として並べる。同じキャラで同じ slot の出場は結合する。同じ slot の別キャラの出場は、並べ替えを全部試す。アタッカーの fill は、続きの出場よりも後ろ。
- `then` の slot は、`use` の slot より大きく、小さい順（build:knowledge が検査する）。
- 辞書の中身は、まだ変えていない（段階 B で、KQM 由来の複数回の形を入れる）。検査: `npm run check:knowledge-seeds`（gcsim なし）。

## 凸数の条件（constellation。2026-11-22）

運用型に `constellation?: { min?, max? }`（0〜6。両端を含む。省略は制限なし）を足した。出発点の組み立て（knowledgeSeeds）は、編成のキャラの凸数（未指定は、星 4 = 6 凸・星 5 = 0 凸）が範囲に入る形だけを使う。凸数で最適な動作が変わるキャラは、範囲ごとに別の形として書く。build:knowledge が範囲を検査する。文章だけで「1 凸」「2 凸」「完凸」と書いていた 5 件に、min を写した。
`scripts/knowledge-kqm-db.ts` は、形ごとに、凸数別（0 凸・1〜5 凸・6 凸）の件数と平均 DPS を出す。ただし、DPS の差は、編成の強さに引きずられる（6 凸の設定は、高 DPS の編成が多い）。形の登録は、件数の偏り（0 凸の設定にだけある形など）を見て決める。

## 出発点の組み立て（2026-11-23 時点）

- 組み合わせ（キャラごとの形の選び方）の基準は 2 つ: 全員が先頭の形（手作り・測定済みの形）と、全員が KQM 由来の形（evidence が `KQM` で始まる形。なければ先頭）。それぞれの基準から 1 人だけ別の形にした組み合わせを全部入れ、残りは全組み合わせから等間隔に取る。
- 出発点の数（と組み合わせの上限）は、画面の「1 段目で残す候補の数」（既定 300）。組み合わせを交互に並べて、この数に切る。
- 辞書の並び: 手作り・測定済みの形を前、KQM 由来の形を後ろに置く（`--apply` も既存の形の後ろに足す）。
- 凸数・続きの出場の扱いは、上の各節のとおり。
- 探索で捨てる条件は、CT 違反などだけ。CT 警告（発動バフ・特殊スキルの受付時間外など）は捨てない。
