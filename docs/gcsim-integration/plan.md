# gcsim 連携 全体計画書

作成: 2026-09-28

## 1. 背景と目的

現状のアプリは、ビルド時に genshin-db と gcsim の Go ソースからフレーム数などのマスターデータだけを抽出し（`src/masterdata/gcsimParser.ts`）、バーの幅・CT・効果時間はアプリ側で計算している（`src/utils/rotationCalculator.ts`）。

これを方針転換し、**gcsim の計算機能を最大限活用する**。キャンセル・CTリセット・武器/聖遺物/固有天賦バフの自動発動など、gcsim が再現する挙動を、ユーザーが編集する値に書き戻してガントチャートに反映する。

### 目標とする流れ

1. ボタンを押すと、その時点の編成を gcsim の設定文（ローテーション文）に変換する
2. gcsim に送って結果（詳細ログ）を受け取る
3. 結果に従って、**ユーザーが編集できる値**（アクションの所要時間・遅延、CT・効果時間、発動バフの位置と継続時間・CT）を上書きする（D20）。上書きした後も、ユーザーは同じ値をこれまでどおり編集できる。ガントチャートの表示は、これらの値からアプリの計算で作る（従来の仕組みを維持）

## 2. 前提

- **ダメージ計算の結果はアプリに反映しない**。時間（アクション・CT・バフ）だけを使う。
- **爆発はCTが空いていれば撃てる**（エネルギー不足で撃てない状態は扱わない）。

## 3. 調査結果（2026-09-28）

gcsim v2.47.6（2026-09-24 リリース）で検証した。

### 3.1 実行方式

- gcsim 公式リリースに `server_<OS>_<arch>` という**ローカルサーバー**がある（gcsim 公式サイトがローカル計算に使う仕組み。ソース: `cmd/server`, `pkg/servermode`）。
- 起動すると `localhost:54321` で待ち受ける。主なAPI:
  - `POST /validate/{id}` `{config}` → 設定文の文法チェック（解析結果のJSON）
  - `POST /sample/{id}` `{config, seed}` → 1回分のシミュレーションの**詳細ログ**を同期で返す
- CORS は `http://*` / `https://*` を許可しているため、**アプリのブラウザ画面から直接 fetch で呼べる**。中継サーバーは不要。
- 実測: アプリ（`http://localhost:3001`）から `/sample` を呼び、約0.4秒で結果を受け取れた。40秒分のログは約1MB・約3,600件。

### 3.2 詳細ログ（Sample）の内容

`logs` はイベントの配列。各イベントは `event`（種類）・`frame`（発生フレーム, 60fps）・`ended`（終了フレーム）・`char_index`・`msg`・`logs`（詳細）を持つ。

| 必要な情報 | 対応するイベント |
|---|---|
| アクションの開始 | `event=action`, `msg="executed skill"` など。交代は `"executed swap"` |
| アクションの終了 | 記録されない → **次のアクションの開始**を終了とする（キャンセル反映済みの実時間） |
| CTの開始・長さ | `event=cooldown`, `msg="skill cooldown triggered"` / `"burst cooldown triggered"`（`logs.expiry` 等） |
| CTの終了 | `msg="... cooldown ready"` |
| CTの短縮・リセット | `"cooldown forcefully reset"` / `"forcefully reduced"` / `"forcefully discarded"` |
| バフの付与・更新・延長 | `event=status`, `msg="... mod added"` / `"mod refreshed"` / `"mod extended"`（`logs.key`=バフのキー名, `logs.expiry`=終了予定フレーム, `ended`=実際の終了フレーム, `char_index`=付与先） |

注意点:
- CTの開始はアクション開始と一致しない（例: ナヒーダ E は発動 0.02s / CT開始 0.20s）。
- バフのキー名は gcsim 内部名（例: `khaj-nisut-team-buff`）。`〜-icd` などの内部管理用も混ざる。チームバフは受け取るキャラごとに1件ずつ記録される。
- 常時効果は `expiry=-1`。
- 繰り返し部分でCT待ちの間、`"could not execute ...; action not ready"`（`event=sim`）が大量に出る（40秒で約1,500件）。読み取り時に除外する。

### 3.3 対象キャラの対応状況

- ナヒーダ・ニィロウ・コロンビーナ・ラウマは、スキル・爆発・固有天賦・命ノ星座まで gcsim に実装済み。実際にシミュレーションが完走した。
- 公式ID→gcsim キーの対応表が gcsim リポジトリにある: `ui/packages/ui/src/data/{character,weapon,artifact}.dm.json`

| 種類 | アプリの件数 | 対応付けできた件数 | 対応付けできないもの |
|---|---|---|---|
| キャラ | 127 | 118 | カチーナ・ネフェル・兹白・ローエン・リンネア・サンドローネ・ヴォジャニーツァ・ヴェスナ・アリョーシャ |
| 武器 | 245 | 234 | 旋流の讃美歌・蝶の羽化・白銀の湖を舞う翼・「一心伝」名刀(3件)・異端を狩る熔刃・銀灯・新たなる枝・雪に沈む心・風に遊ぶ弦 |
| 聖遺物 | 63 | 55 | 火/水/氷/雷祭りの人・奇跡・医者・幸運・冒険者（★1〜3） |

旅人は gcsim では空（`aether<元素>`）と蛍（`lumine<元素>`）が別キー。アプリのキャラデータは現状 `aether<元素>` を持っている。

### 3.4 gcsim の設定で使うもの

- `options ignore_burst_energy=true` : 爆発の可否をCTだけで判定する（前提2に対応）。
- `options swap_delay=<frames>` : 交代遅延（アプリの交代遅延を変換）。
- `options hitlag=true`（既定）: ヒットストップを含める。
- `delay(<frames>)` : 直前のアクションの**終了後**に、次のアクションの開始を遅らせる（アクション遅延に使う）。※ `sleep`/`wait` はアクション途中から数えるため使わない。
- `target lvl=100 resist=0.1;` : **`hp` を指定しない**。指定すると `duration` が無視され撃破まで走る（検証時に約8時間分・ログ750MBになった）。

### 3.5 初動とループ（0s基準）の検証（2026-09-28）

アプリの「0s基準」（出場の間に置き、1周目だけの初動と、2周目以降も繰り返すループ部分に分ける機能）が gcsim で扱えるかを検証した。

- **設定文への変換**: 初動を先に書き、ループ部分を回数指定の `while` で囲めば表現できる。`print("loop ", i)` で周の区切りがログ（`event=user`）に残るので、どのアクションが何周目かを確実に判別できる。
  ```
  active nahida;
  nahida skill, burst;          # 初動（1周目だけ）
  let i = 1;
  while i <= 4 {
    print("loop ", i);          # 周の区切りの目印
    nilou skill, attack:3;      # ループ部分
    ...
    i = i + 1;
  }
  ```
- **CTが間に合うローテーション**: ループ1周目から全周の時間が完全に一致した（例: 1周 18.13秒、各アクションの周内の相対時刻も一致、CT待ち 0件）。アプリの「1つの時間軸を1周目と2周目以降で共有し、折り返しを重ねる」表示とそのまま対応する。
- **CTが間に合わないローテーション**（ループ部分がCTより短い）: gcsim はアプリのように「CT違反」を表示するのではなく、**CTが空くまで待ってから**アクションを出す。そのため周ごとに時間が変わり、4周しても一定にならなかった（例: ナヒーダ初動＋ニィロウ→コロンビーナ→ラウマ→コロンビーナのループで、各周の長さ 7.8秒 / 31.8秒 / 17.6秒 / …）。待っていた区間は `could not execute <action>; action not ready`（`event=sim`）の連続として、開始・終了の時刻が取れる。
- **折り返し（持ち越し）**: gcsim は周をまたいで連続して計算するので、2周目以降の先頭に前の周から続くCT・効果は、実際のスパンをそのまま切り出せば得られる（アプリ側で折り返しを計算する必要はない）。

| D21 | CT待ちの扱い | ボタン押下時にアプリの既存のCT違反があれば解消を促して計算しない。計算前に違反が無くても gcsim の結果でCT待ちが生じたら、書き戻さずに違反マークを付ける。CTが間に合わない周が無くなるため、1周目と2周目以降で結果が異なることは起きない（フェーズ6） |

## 5. CT・効果時間の管理構造の分析（2026-09-28）

現状のアプリは CT・効果時間を4分類で管理している。

| 分類 | 定義の出どころ | 発動位置 | バーのデータ |
|---|---|---|---|
| スキル・爆発 | アクション定義の `cooldown` / `effectDuration` | アクションの位置から自動 | `CooldownSpan`, `ActiveBuffSpan`(origin=action) |
| 固有天賦 | `PassiveEffectDefinition` | ユーザーがドラッグで配置 | `PassiveSpan`(category=talent) |
| 武器効果 | `EquipmentBuffDefinition`(`wbuff_`) | 同上 | `PassiveSpan`(category=weapon) |
| 聖遺物効果 | `EquipmentBuffDefinition`(`abuff_`) | 同上 | `PassiveSpan`(category=artifact) |

### 入力側（アクション構築 → gcsim 設定文）: 構造の変更は不要

- gcsim の入力に必要なのはキャラ・凸数・武器・精錬・聖遺物（4セット/2+2）・アクションの並びだけ。CT・効果時間の秒数も4分類の区別も渡さない（gcsim が自前のデータで計算し、武器・聖遺物・固有天賦のバフは条件に従って自動発動する）。
- 発動バフのドラッグ配置、アクションごとのCT・効果時間の手動上書きは gcsim に渡す手段がない（未決事項 O1）。

### 出力側（gcsim の結果 → ガントチャート）: 構造の変更が必要

- 分類が明確なのはスキル・爆発のCT（`cooldown` イベント）だけ。効果は `status` イベントとして、分類を示す項目なしに同じ形で混ざって出る。
- キー名の付け方が統一されておらず、名前の規則では分類できない。
- 固有天賦・武器・聖遺物のCTは `〜-icd` などのステータスとして出て、内部クールダウンと混ざる。CTと効果の紐付けも必要。
- 4分類に収まらないもの（命ノ星座・元素共鳴・システム効果・敵デバフ・常時効果）が出る。
- チームバフは受け取るキャラごとに記録される（アプリは発動元の行に表示する）。
- → キー名の定義場所で分類がほぼ機械的に決まることを確認し、D10（キーの辞書）・D11（共通の型）を決定。

## 6. 全体構成（完成時）

```
[編成・出場・アクション]
      │ フェーズ4: 変換（gcsimKey・4セット/2+2・delay・ignore_burst_energy など）
      ▼
[gcsim 設定文] ──POST /sample──▶ [gcsim ローカルサーバー localhost:54321]
                                         │ 詳細ログ（action / cooldown / status）
      ◀────────────────────────────────────┘
      │ フェーズ6: ログを読み取り、編集できる値へ書き戻す（D20）
      │            （バフの分類・発動元は キーの辞書 で引く ← フェーズ5 でビルド時に生成）
      ▼
[編成・出場・アクションの値（ユーザーが引き続き編集可能）]
      │ 従来のアプリの計算
      ▼
[ガントチャート]
```

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| gcsim の更新でログ形式・キー名が変わる | 対応バージョンを記録し、読み取り処理を1か所にまとめる。未知のイベントは無視する |
| gcsim 未対応のキャラ・武器が編成に含まれる | 変換前に検出して利用者に知らせ、gcsim 実行を行わない（従来の計算で表示を続ける） |
| ローカルサーバーが起動していない | 呼び出し失敗時に起動手順を案内する |
| 祭礼リセットの種が見つからない | 探索回数に上限を設け、見つからなければ警告を出して最良の結果を使う |
| gcsim のキー名の分類を誤る・新しいキーが分類されない | キーの辞書を gcsim ソースから自動生成し（D10）、未判定キーをレポートで確認する。読み取り時に辞書に無いキーは除外して記録する |

## 10. 関連する未対応事項（本計画の範囲外）

- 武器・聖遺物の補正辞書の CT・効果時間は、実行時（`buffUtils.ts`）に精錬ランクを問わず上書きされる（例: 祭礼の断片は精錬5の CT16秒が精錬1にも適用される。本来30秒）。gcsim 連携後は結果ベースになるため、従来計算を残す場合のみ修正が必要（フェーズ2で発見）。

- 武器・聖遺物の効果時間の読み取りパターンが「継続時間は○秒」（「は」付き）に対応していない（`equipmentBuffParser.ts` の `extractEquipmentTimings`）。例: 狼の武勲詩は効果時間が取れず、フェーズ1の I1 修正後は発動バフの定義が無くなった。gcsim 連携後は結果ベースになるため、従来計算を残す場合のみ修正が必要。

- 発動バフCTの折り返しバーの長さが、折り返し後の時刻に変換されていない（`rotationCalculator.ts` の発動バフ折り返しで `cooldownEnd` が1周目の時刻のまま）。gcsim 連携後は結果ベースになるため、従来計算を残す場合のみ修正が必要。
