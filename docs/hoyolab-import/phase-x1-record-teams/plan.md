# PhaseX1 計画: 戦績（深境螺旋・幻想シアター・幽境の危戦）の使用編成を取り込む

状態: **案（2026-11-18）。未着手**。親計画: [../plan.md](../plan.md)（HoYoLAB 持ちキャラ取り込み）・設計: [../design.md](../design.md)。進捗: [progress.md](progress.md)。

> **この文書の根拠**: genshin.py（MIT。v1.7.32）のソースとドキュメントを読んだ結果。**HoYoLAB の実際の応答は、まだ 1 件も確認していない**。項目名・形・他アカウントの可否は、フェーズ X1-0（実機確認）で確かめ、結果でこの文書を直す。

## 1. 目的

HoYoLAB の戦績に残っている「挑戦で実際に使った編成（4 人）」を取り込み、**編成のたたき台**としてワンクリックで読み込めるようにする。

- 持ちキャラ取り込み（既存）は「持っているキャラの装備」を取り込む。PhaseX1 は「どのキャラを組み合わせて使ったか」を取り込む。この 2 つを組み合わせると、「前回の深境の編成を、今の装備のまま、ローテーション作成の出発点にする」ことができる。
- 入力の手間（キャラ 4 枠を 1 つずつ選ぶ）を減らす。

## 2. 範囲

### 含む
1. 拡張機能（`extension/hoyolab-importer`）に、戦績の取得を足す（既存の署名・Cookie の扱いをそのまま使う）。
   - 深境螺旋（今期・前期）
   - 幻想シアター（過去の期を含む）
   - 幽境の危戦（取得できた期すべて）
2. アプリで、取得結果を「使用編成（`RecordTeam`）」の一覧に変換し、画面で選んで、新しい編成として読み込む。
3. 読み込むとき、そのキャラが**持ちキャラに取り込み済みなら、装備（武器・聖遺物・天賦・凸）を反映**する（既存の `ownedToPartyFields`）。

### 含まない（別の作業・将来）
- **敵情報の自動入力**（幽境の危戦の敵のレベル → `EnemySetting`）。→ §8 の拡張候補 X1-b。
- **実際のクリア時間・DPS とアプリの計算結果の比較**（拡張候補 X1-c）。
- 他のアカウントの UID の戦績（§4 の確認結果しだい。既定では対象外）。
- 戦績の長期保存・履歴の管理（保存しない。§5）。
- 中国サーバー（米游社）。親計画の決定どおり、HoYoLAB の海外版のみ。

## 3. genshin.py から分かっていること（要実機確認）

genshin.py の実装（`genshin/client/components/chronicle/genshin.py` と `models/genshin/chronicle/`）による。URL の前半は、持ちキャラ取り込みと同じ `https://sg-public-api.hoyolab.com/event/game_record/genshin/api/`。

| 種類 | エンドポイント | 方式・パラメータ | 編成に使える項目 |
|---|---|---|---|
| 深境螺旋 | `spiralAbyss` | GET。`role_id`・`server`・`schedule_type`（1=今期、2=前期） | 階（`floors[].index`）→ 間（`levels[].index`）→ 前半・後半（`battles[].index`）ごとの 4 人。各キャラは `id`・`name`・`element`・`rarity`・`level`（凸・装備は無し）。星の数・挑戦期の開始/終了時刻 |
| 幻想シアター | `role_combat` | GET。`role_id`・`server`・`need_detail=true`。期の指定は無く、過去の期の分も返る（`data[]`） | 幕（`rounds_data[]`）ごとのキャラ（`avatars[]`: `id`・`name`・`element`・`rarity`・`level`・`avatar_type`。**1=所持キャラ・2=試用キャラ・3=助っ人（他の人のキャラ）**）。難易度・幕の完了日時 |
| 幽境の危戦 | `hard_challenge` | GET。`role_id`・`server`・`need_detail=true`。`data[]` に期ごと（`schedule.is_valid` のものだけ使う） | 難易度ごとの挑戦（`challenge[]`）。チーム（`teams[]`: `avatar_id`・`name`・`element`・`rarity`・`level`・**`rank`=凸**）、クリア時間（`second`）、敵（`monster`: 名前・レベル・説明・元素タグ）、キャラごとの DPS（`best_avatar[].dps`） |

- キャラ ID（`id` / `avatar_id`）は、持ちキャラ取り込みと同じ**ゲーム内のキャラ ID**で、マスターの `<id>-<元素>` の前半と対応づけられる（[../plan.md](../plan.md) の「ID の対応」）。旅人・ドール・gcsim 未対応のキャラは、既存の扱い（編成に入れられない理由を表示）に従う。
- **戦績の応答には、武器・聖遺物の情報が無い**。装備は、持ちキャラの取り込み結果から補う。持ちキャラに無いキャラ・助っ人・試用キャラは、従来の仮値（Lv90・天賦 9,9,9 など）で入る。
- 幽境の危戦の敵は、元素の**種類のタグ**までで、耐性の数値は返らない（X1-b の制約）。
- 署名（`ds`）・ヘッダーは、持ちキャラ取り込みと同じ。`host_permissions`（`sg-public-api.hoyolab.com`）も変えなくてよい見込み（**拡張機能のマニフェストの権限は増やさない**）。

## 4. 実機で確かめること（フェーズ X1-0）

試作は、[tools/hoyolab-fetch/console_fetch.js](../../../tools/hoyolab-fetch/console_fetch.js) と同じ方式（`act.hoyolab.com` のコンソール）で行い、応答の JSON は**個人情報（UID・プレイヤー名）を除いてから**、検査用の資料にする。

1. 3 つのエンドポイントとも、ご自身の UID で、応答が返るか。戦績の「公開設定」をオフにしても返るか（持ちキャラの詳細では、公開設定に関係なく返った。同じとは限らない）。
2. 実際の項目名・形が、§3 の表（genshin.py のモデル）と一致するか。違いがあれば、表を直す。
3. **他のアカウントの UID** で拒否されるか（持ちキャラの詳細は 10104 で拒否された）。拒否されるなら、他の UID は対象外（Enka.Network に戦績は無い）。
4. 期の扱い: 深境の今期・前期、幻想シアターの過去の期、幽境の危戦の期が、どこまで取れるか。挑戦していない期は、空か、エラーか。
5. キャラ ID が、持ちキャラの `genshinId`・マスターの ID と一致するか（旅人・助っ人・試用キャラの扱いを含む）。
6. 回数制限: 1 回の取り込みで、何リクエストまで問題なく通るか（見込みは、深境 2 + 劇場 1 + 幽境 1 = 4 回）。

## 5. 設計（案。X1-0 の結果で見直す）

### データの持ち方
- **戦績は保存しない**（メモリだけ）。理由: 期の入れ替わりで古くなる／UID・挑戦履歴という個人情報が入る／持ちキャラ取り込みの設計（生の JSON は保存しない）と同じ。
- 取得 → `RecordTeam[]` に変換 → 画面で選ぶ → 選んだ 1 編成だけを、**通常の編成（`PartyMember[]`）に変換して保存**する（既存の保存・共有 URL・バックアップの仕組みに乗る）。`localStorage` は `persistence.ts` 経由のみ。新しい保存項目は作らない。

```ts
// 案（src/utils/hoyolab/recordTeams.ts）
type RecordKind = 'abyss' | 'theater' | 'stygian';
interface RecordTeam {
  kind: RecordKind;
  /** 画面の見出し用（期・階・間・半・幕・難易度など。言語に依存しない値で持ち、表示で翻訳する） */
  label: { season?: number | string; floor?: number; chamber?: number; half?: 1 | 2; act?: number; difficulty?: number };
  /** 4 人（劇場は幕により 4 人。順序は戦績どおり） */
  members: { genshinId: number; name: string; element: string; level: number; constellation?: number; role?: 'normal' | 'trial' | 'support' }[];
  /** 幽境の危戦のみ（X1-c）。クリア時間（秒） */
  clearSeconds?: number;
}
```

### 変換の規則
- キャラ: ゲーム内 ID → マスターのキャラ ID（既存の対応表。旅人は取得時の元素で決める）。マスターに無い・gcsim 未対応は、「編成に入れられない」（理由を表示）。
- 装備: 持ちキャラ（`loadOwned()`）に同じ ID があれば `ownedToPartyFields` の結果を使う。なければ仮値。**「挑戦したときの装備」ではなく「今の装備」**であることを画面で明記する。
- 凸: 持ちキャラがあれば持ちキャラの値、無ければ戦績の値（幽境の危戦のみ。深境・劇場には無い）、それも無ければ従来の既定。
- 助っ人・試用キャラ（劇場）: 持ちキャラの装備は使わない。一覧に印を付ける。
- 同じ編成（4 人の組が同じ）の重複は、まとめて 1 件にして、使われた場所を併記する。

### 拡張機能
- メッセージ `hoyolab-fetch-records`（`{ uid, kinds: ('abyss'|'theater'|'stygian')[] }`）を追加。応答 `hoyolab-records-result`。既存の `hoyolab-fetch` と同じ作法（`requestId`・タイムアウト・`retcode` を返す）。
- `hoyolab.js` に `fetchRecords(uid, kinds)` を追加。GET でクエリを付ける（`index` の取得と同じ書き方）。順番に、少し間を置いて取得する（既存の `fetchOneByOne` と同じ配慮）。
- 版を上げる（0.2.5 → 0.3.0）。アプリ側は `extensionVersion.ts` で、新しい機能に必要な版を確認し、古い版なら更新の案内を出す。
- Cookie の値は読まない・`cookies` 権限は足さない・外部への送信はしない（既存の方針のまま）。

### 画面
- 入口: 取り込み画面（`OwnedCharactersModal`）の中に「戦績から編成を読み込む」の節を足すか、独立したダイアログにするか → **決定が要る（§7 の 1）**。
- 一覧: 種類（深境・劇場・幽境）のタブ、期・階・間・半などの見出し、4 人のアイコン（Lv・凸）、「持ちキャラの装備あり／なし」「編成に入れられないキャラあり」の印。
- 操作: 選ぶ →「この編成を新しい編成として読み込む」→ 既存の編成の作り方（空の編成に 4 枠を入れる）。**現在開いている編成を上書きしない**（確認ダイアログか、新しい編成として作る）。
- 文言は ja / en の両方（`npm run check:i18n`）。ヘルプ（`guide.json` の `owned` の節）・`docs/privacy.md`（戦績の取得を追記。外部に送らないこと）も更新。

## 8. 拡張候補（PhaseX1 では実装しない）

- **X1-b 敵のレベルの自動入力**: 幽境の危戦の `monster.level` → DPS 計算の `EnemySetting.level`（[buildGcsimConfig.ts](../../../src/utils/gcsim/buildGcsimConfig.ts) の `targetStatements`）。耐性は数値が取れないので、既定の値のまま。
- **X1-c 実際のクリア時間・DPS の表示**: 戦績の `second`・`dps` を、アプリの計算結果の隣に出す。ただし、実戦の時間は敵の HP・操作の差を含み、ローテーションの時間とは意味が違う。**比較としての価値があるかを、別途相談**してから。

## 9. リスク・注意

| リスク | 対応 |
|---|---|
| 非公式 API のため、仕様変更・取得できなくなる可能性 | 失敗時は、わかりやすいメッセージ（retcode ごと）を出し、既存の機能（手動の編成）はそのまま使える |
| 戦績の応答の形が、genshin.py と違う | X1-0 で実物を確かめてから実装する。変換は、足りない項目があっても落ちない書き方（検査で確認） |
| 「今の装備」が、挑戦時と違う | 画面に明記する。装備を使わず、キャラだけ読み込む選択肢も用意する（§7 の 5 と合わせて検討） |
| Cookie・個人情報 | 既存の方針（値を読まない・保存しない・外部に送らない）を守る。見本の JSON は、UID・プレイヤー名を除いてからコミットする |
| 回数制限 | 4 リクエスト程度。間を置いて順番に送る |
| genshin.py のライセンス | MIT。実装を参考にするだけで、コードは取り込まない。`NOTICE` の出典の URL は、現在の `seriaati/genshin.py` に直す（別作業） |
