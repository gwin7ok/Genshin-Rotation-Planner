# 多言語対応（日本語 / 英語） 計画書

## 1. 要件（ユーザー指示 2026-10-29）

- アプリ全体を、日本語 / 英語の 2 つのモードに対応させる。
- 日本語・英語とも言語ファイルを作り、どちらを使うかで切り替える。
- 選択された言語は、ブラウザのローカルストレージに設定として保存する。
- 設定が無いときは、ブラウザの言語設定に従って選ぶ。

## 2. 調査結果（2026-10-29）

### 2.1 保存容量の見積もり（D250 の影響）

- genshin-db の文字列の値だけを比べると、英語は日本語の **約 2.4 倍** の文字数（天賦・武器で測定。ja 約 83 万字 / en 約 199 万字）。
- 今の DB の日本語の文字は約 55 万字 → 英語を足すと **約 +130 万字**。DB は **約 300 万字** になる見込み（保存編成を除く）。
- localStorage の上限は、Chrome・Firefox で約 500 万字。Safari はより小さい可能性がある（未確認）。
- 対策: フェーズ 3 の最初に実際のサイズを測る。足りない場合は、保存先を IndexedDB へ移すことを相談する（`persistence.ts` は保存先を差し替えられる）。

## 4. 構成

### 4.1 ファイル

```
src/i18n/
  index.ts          … i18next の初期化（起動時に 1 回。言語の決定 → init）と、文言を引く t()
  language.ts       … 言語の決定（設定 → ブラウザ）・保存・切り替え（再読み込み）
  resources.ts      … 言語ファイルの一覧（名前空間を足したら ja・en の両方をここに足す）
  keys.ts           … キーの型（ja の言語ファイルから作る。キーの打ち間違いを tsc で検出する）
src/components/LanguageSwitcher.tsx … 切り替え（ヘッダーの「省略」ボタンの隣）
src/locales/
  ja/<名前空間>.json … 例: common.json, header.json, gantt.json, …
  en/<名前空間>.json
scripts/check-i18n.ts … ja と en のキーの一致、未訳（en に日本語が残る）の件数
docs/i18n/glossary.md … 用語集
```

### 4.1.1 文言の引き方

- コンポーネントでも React の外でも、`src/i18n` の `t()` を使う（例: `t('language.auto')`、`t('header:menu.help')`）。言語は実行中に変わらないため、`useTranslation` は要らない。
- i18next の型の宣言（`CustomTypeOptions`）は使わない。i18next の型は `strictNullChecks` が前提で、このプロジェクト（無効）では、名前空間なしのキーが通らないため（2026-10-29 に確認。有効にすると、`src/utils/rotation/` などに 12 件の型エラーが出る）。代わりに `keys.ts` でキーの型を自前で作る。
- 差し込み値の名前の正しさは型で検査しない（`check:i18n` が ja と en で同じかを検査する）。
- 文の中に部品（太字・リンク）を含めるときは、react-i18next の `Trans` を使う。

### 4.2 言語の決め方（D245〜D248）

1. `SETTING_KEYS.language`（`'ja'` | `'en'`）があれば、それを使う。
2. 無ければ `navigator.languages` を先頭から見て、最初に `ja` / `en`（地域つき `ja-JP`・`en-US` を含む）に一致したもの。どちらも無ければ `en`。
3. 自動の判定の結果は保存しない（「自動」を選ぶと、保存を消す）。
4. 切り替えたら、保存してからページを再読み込みする。言語は起動時に 1 回だけ決まり、実行中は変わらない。
   - そのため、React の外（`src/utils/`・`src/masterdata/`）の文言も `i18n.t()` で引ける（`src/i18n/index.ts` を `main.tsx` の最初で読み込み、ほかのモジュールより先に初期化する）。
5. 公開（D253）までは、本番のビルドでは常に日本語にし、切り替えを表示しない（`import.meta.env.DEV` のときだけ有効）。英語のブラウザの人に、訳しかけの英語を出さないため。

### 4.3 ゲームデータ（D249・D250）

- マスターの生成で、表示用の文（名前・天賦名・説明文）を英語でも持つ。数値の抽出は日本語の文から行い、英語の文からは行わない。
- アプリ独自の名前（効果名・要約など）は、日本語と英語の両方を定義に書く。自動生成の要約（例「旧貴族4: 全員攻撃力+20%」）は、抽出した値から両言語の文を組み立てる。
- 保存編成・プリセットの中の名前は、表示のときに DB から ID で引く。保存されている名前は、DB に無いもの（削除済み・カスタム）の代わりにだけ使う。
- 名前の文字列で判定している処理は、種類・ID で判定する形に直す。

#### 4.3.1 DB の形（D255〜D258。2026-10-29）

- **英語の欄をまとめて足す**（D255）: 文を持つ各オブジェクト（キャラ・アクション・命ノ星座・固有天賦の効果・武器・精錬・発動バフ・聖遺物など）に `en?: { name?: string; description?: string; ... }` を足す。日本語の欄（`name` など）は今のまま。
  - 表示は、共通の関数（例 `loc(obj, 'name')`）で、英語のときは `obj.en?.name ?? obj.name`、日本語のときは `obj.name`。
  - `en` が無い古いデータ（保存済みの DB・バックアップ・ロック中・カスタム）は、日本語で出る。移行処理は要らない。
  - 処理（数値の抽出・ID の判定・gcsim の設定文）は、今までどおり日本語の欄だけを見る。
- **容量はそのまま足す**（D256）: 見積もりは DB 約 340 万字（今 174 万字）。日本語の文 69 万字のうち 37 万字は重複だが、減らさない。保存に失敗したときの警告と書き出しの案内は既存のもの。
- **DB 管理の編集は、表示中の言語の欄**（D257）: 英語の画面では `en` の欄、日本語の画面では今の欄を編集する。
- **要約は英語で組み立て、根拠の引用も英語の説明文から探す**（D258）: 効果名・要約は、抽出した値から英語の文を作る。継続時間・CT の根拠の引用（`dataSource`）は、英語の説明文から同じ値の箇所を探して `en.dataSource` に入れる。見つからないときは日本語の原文を出す。

#### 4.3.2 フェーズ 3 の進め方

| 段階 | 内容 |
|---|---|
| 3-1 | 型（`en` の欄）と表示の関数。DB の読み込み・同期・バックアップで `en` を保つ。画面の名前・説明の表示を関数に置き換える |
| 3-2 | マスターの生成で英語を取得（genshin-db の English。キャラ名・天賦名・説明文・命ノ星座・武器・精錬・聖遺物） |
| 3-3 | アプリ独自の定義（`src/masterdata/` の効果名・モードの名前・説明・ヒント）に英語を足す |
| 3-4 | 要約の英語の組み立てと、英語の説明文からの根拠の引用（D258） |
| 3-5 | 名前で判定している処理を、ID・種類での判定に置き換える |
| 3-6 | 保存編成・プリセットの名前を、表示のときに DB から ID で引く |
| 3-7 | マスターを作り直し、`check:snapshots` で差を説明してから保存。保存容量を実測する |

## 6. リスク・注意点

- 保存容量（2.1）。
- 英語は長くなりやすく、ガントチャートのラベル・狭いボタンではみ出す → 各フェーズで画面を確認する。
- 利用者が作ったカスタムのキャラ・武器の名前は、入力した 1 言語のまま。
- `check:snapshots` などの検査が名前を比べていると、結果が変わる可能性がある → フェーズ 3 で確認する。
- 対象外: `CHANGELOG.md`・`docs/`・README・Issue テンプレート・ソースのコメント・console のログ（開発者向け）。
