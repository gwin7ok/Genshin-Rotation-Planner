# リリース手順（バージョン管理・公開）

2026-10-12 に決定（D177・D179）。公開先: GitHub Pages（https://gwin7ok.github.io/Genshin-Rotation-Planner/）。

**基本は、VSCode の 2 つのキーで、リモートの公開まで行う。**

| キー | タスク | 内容 |
|---|---|---|
| `ctrl+shift+2` | **Update Changelog** | 更新履歴の更新と、版の更新（`npm run release:bump`） |
| `ctrl+shift+3` | **release-tag-and-push-short** | コミット → push → タグ → Actions が Release の作成と公開（`npm run release:tag`） |

参考にした仕組み: `G:\Cursor_Folder\WRFFofGwin\firefox-window-resizer`（`tools/bump-version.ps1`・`tools/release-tag.ps1`・`.github/workflows/release.yml`）。同じ流れを、このプロジェクト（Node + GitHub Pages）に合わせた。

## 版の決め方
- **セマンティックバージョニング**（`主.副.修正`）。出どころは `package.json` の `version`（唯一）。
  - 主: 保存データの互換を壊す変更（バックアップの `version`・保存形式の変更など）、大きな作り直し。
  - 副: 機能の追加（互換あり）。gcsim のバージョンを上げたとき（結果が変わりうる）も、副を上げる。
  - 修正: 不具合の修正・表示の変更・文書。
- タグは `v<版>`（例: `v1.1.0`）。`main` のコミットに付ける。
- 画面のフッターに「バージョン v<版>（コミット <短縮>）」を表示する（ビルド時に埋め込み。`vite.config.ts`・`src/utils/appVersion.ts`）。
- 全データのバックアップには、`app.version`（書き出したときの版）を記録する。
- gcsim の版（`gcsim.config.json`）は、アプリの版とは別に管理する（画面の下部・バックアップに併記）。

## 変更履歴（`CHANGELOG.md`）
- 日本語。Keep a Changelog 形式（追加・変更・修正）。リリースノート（GitHub Release の本文）の原本になる。
- 利用者に見える変更だけを書く（内部の決定 D 番号・計算の内部の変更は、`docs/gcsim-integration/progress.md`）。
- 手で `[Unreleased]` に書いてもよい。空のままなら、Update Changelog が、前のリリース以降のコミットから生成する。

## 通常のリリースの流れ
1. 機能の追加・修正を、ブランチで行い、コミット → PR → `main` にマージ（あなた）。
2. `main` で、**`ctrl+shift+2`（Update Changelog）**:
   1. `[Unreleased]` が空なら、前のリリース（最新のタグ `v*`）以降のコミットから生成した内容を確認する（`Enter` = 書き込んで続行 / `e` = 書き込んで編集 / `n` = 中止）。
      - 載せる種類: `feat` → 追加、`fix` → 修正、`refactor`・`perf`・種類なし → 変更。載せない種類: `docs`・`test`・`chore`・`ci`・`style`・`build`・`Release v…`・`Merge …`。
      - コミットの 1 行目が、そのまま文になる（先頭の決定番号 `D177 ` は外す）。**利用者に分かる文に、後で直す**。
   2. 次の版を選ぶ（1 = パッチ / 2 = マイナー / 3 = メジャー / `x.y.z` を直接入力）。
   3. `package.json` の `version` を更新し、`CHANGELOG.md` の `[Unreleased]` を `[x.y.z] - 日付` に切り出す（末尾の比較リンクも更新）。
3. `CHANGELOG.md` の文を確認・編集する（コミットはまだしなくてよい）。
4. **`ctrl+shift+3`（release-tag-and-push-short）**:
   1. 前提の確認: 版の節が `CHANGELOG.md` にある・タグが未作成（ローカル・リモート）・`main` ブランチ・`origin/main` より遅れていない・`package.json` と `CHANGELOG.md` 以外に未コミットの変更がない。
   2. 公開前の検査（`check:release`）。
   3. 確認（`Enter` = 実行 / `n` = 中止）→ `Release vX.Y.Z` をコミット → `main` を push → 注釈付きタグ → タグを push。
5. **以降は、Actions が自動で行う**（`.github/workflows/release.yml` → `deploy.yml`。数分）:
   1. 版の検証（タグ = `package.json` の version・タグのコミットが `main` に含まれる）。
   2. `CHANGELOG.md` から、その版の節を抽出して、**GitHub Release を作成**。
   3. **deploy（GitHub Pages への公開）を起動**（タグのソースをビルド → `check:release` → 公開）。
6. 公開サイトで、フッターの「バージョン v<版>」と、「gcsim で計算」の動作を確認する。

事前の確認だけをしたいときは、タスク `release-tag: dry run`・`Update Changelog: dry run`（何も実行・変更しない）。

## 最初のリリース（v1.0.0）
- `package.json` は `1.0.0`、`CHANGELOG.md` に `[1.0.0]` の節があり、タグが未作成なので、**`ctrl+shift+2` は不要**（実行しても、「`ctrl+shift+3` でリリースできます」と案内される）。
- 先に、未コミットの変更（`.github/workflows/`・`.vscode/`・`scripts/` など）を、コミットして `main` に push する。
- その後、`ctrl+shift+3`。

## なぜ、タグの push から deploy を直接起動しないか
`github-pages` 環境は、既定で `main` ブランチからのデプロイだけを許可する（タグ起点の deploy は、保護ルールで拒否される。2026-10-12 に確認）。
そのため、タグ起点の `release.yml` が、`gh workflow run deploy.yml --ref main -f ref=<タグ>` で、**main の上で**deploy を実行する（公開するソースは `ref` でタグを指定）。環境の保護ルールを緩めずに済む。
（Actions の `GITHUB_TOKEN` による `workflow_dispatch` は、許可されている。`release.yml` に `permissions: actions: write` を指定している。）

## 手動での公開（予備）
Actions の `deploy` → Run workflow（ブランチ `main`。`ref` に、公開したいタグを入れる。空なら main の先頭）。

## gcsim のバージョンを上げるとき
`docs/gcsim-サーバー更新手順.md`（6-B: WASM の再ビルドとフォークのタグ `app-wasm-<gcsim の版>`）を行ってから、上の流れ（副を上げる）に進む。
同梱のプリセット編成（`src/data/presets/*.json`）の反応の行は、gcsim のバージョンが違うと出なくなる（古い結果を出さないため）。必要なら、画面で「gcsim で計算」→ 保存 → JSON を書き出し → 同名のファイルを置き換える（`exportedAt` は消す）。

## 失敗したとき
| 症状 | 対処 |
|---|---|
| `ctrl+shift+3` が、「タグがすでにある」と止まる | 版を上げる（`ctrl+shift+2`）。タグの再作成・削除はしない（公開した版は、付け直さない） |
| Actions の `release` が、「タグが package.json と違う」で失敗 | タグを付けた後に、`package.json` を変えた。新しい版で、やり直す |
| `release` の「deploy を起動」が 403 | リポジトリの Settings → Actions → General → Workflow permissions を確認。予備の手動の公開（上）で公開する |
| `deploy` の `check:release` が、フォークのタグで失敗 | `docs/gcsim-サーバー更新手順.md` の 6-B（`app-wasm-<版>` のタグ） |
| Release はできたが、公開されない | Actions の `deploy` の結果を確認。直したら、予備の手動の公開 |

## 更新の通知（利用者のブラウザ）
- **判定は、アプリの版ではなく、DB（マスターデータ）のバージョン（`src/data/databaseMaster.ts` の `DATABASE_VERSION`）で行う**（D198）。ブラウザに、利用者が最後に確認した DB のバージョン（`app_last_seen_db_version`）を記録する。ページの読み込み時に、今の `DATABASE_VERSION` のほうが新しければ、「DB管理で、キャラ・武器・聖遺物のマスターデータを、全削除 → 動的生成してください」というポップアップを、1 度だけ出す（`src/utils/versionNotice.ts`・`UpdateNoticeModal.tsx`）。
- **運用ルール: 同梱のマスターデータの内容・構造を変えたら、`DATABASE_VERSION` を上げる**（もともとの運用。上げると、保存 DB の同梱マスターへの自動の置き換えと、この通知の両方が働く。1 つの番号に統一している）。アプリの版（x.y.z）は、通知に関係しない。
- 記録がない利用者（この機能の導入前から使っている人）は、保存 DB の `version` で判定する（今と同じなら出さない）。自動の置き換えで `version` が書き換わる前に、`loadDatabase` が、記録として残す。
- 初めての利用者（DB がない）には出さない（同梱の最新のマスターが使われるため）。古いアプリを開いたときは、記録を進めない。
- 確認: `npm run check:version-notice`。

## 注意
- `package.json` の `version` は、`npm version` ではなく、Update Changelog で変える。
- 公開した版のタグは、消さない・付け直さない（フォークの `app-wasm-*` タグも同じ）。
- Release を作る Actions と、公開の Actions は別の実行。**Release が先に作られ、公開は数分後**に終わる。
