# リリース手順（バージョン管理・公開）

2026-10-12 に決定（D177・D179）。公開先: GitHub Pages（https://gwin7ok.github.io/Genshin-Rotation-Planner/）。

**基本は、VSCode の 2 つのキーで、リモートの公開まで行う。**

| キー | タスク | 内容 |
|---|---|---|
| `ctrl+shift+2` | **Update Changelog** | 更新履歴の更新と、版の更新（`npm run release:bump`）。続けて `npm run build` で `dist` を作り直す（公開前の検査が、`dist` と `public` の main.wasm が同じかを見るため） |
| `ctrl+shift+3` | **release-tag-and-push-short** | コミット → push → タグ → Actions が Release の作成と公開（`npm run release:tag`） |

参考にした仕組み: `G:\Cursor_Folder\WRFFofGwin\firefox-window-resizer`（`tools/bump-version.ps1`・`tools/release-tag.ps1`・`.github/workflows/release.yml`）。同じ流れを、このプロジェクト（Node + GitHub Pages）に合わせた。

## 版の決め方
- **セマンティックバージョニング**（`主.副.修正`）。出どころは `package.json` の `version`（唯一）。
  - 主: 保存データの互換を壊す変更（バックアップの `version`・保存形式の変更など）、大きな作り直し。
  - 副: 機能の追加（互換あり）。gcsim のバージョンを上げたとき（結果が変わりうる）も、副を上げる。
  - 修正: 不具合の修正・表示の変更・文書。
- タグは `v<版>`（例: `v1.1.0`）。`main` のコミットに付ける。
- 画面のフッターに「バージョン v<版>（コミット <短縮>）」を表示する（ビルド時に埋め込み。`vite.config.ts`・`src/utils/appVersion.ts`）。
- 全データのバックアップには、`app.version`（書き出したときの版）を記録する。
- gcsim の版（`gcsim.config.json`）は、アプリの版とは別に管理する（画面の下部・バックアップに併記）。

## 変更履歴（`CHANGELOG.md`）
- 日本語。Keep a Changelog 形式（追加・変更・修正）。リリースノート（GitHub Release の本文）の原本になる。
- 利用者に見える変更だけを書く（内部の決定 D 番号・計算の内部の変更は、`docs/gcsim-integration/progress.md`）。
- 手で `[Unreleased]` に書いてもよい。空のままなら、Update Changelog が、前のリリース以降のコミットから生成する。

## 通常のリリースの流れ
1. 機能の追加・修正を、ブランチで行い、コミット → PR → `main` にマージ（あなた）。
2. `main` で、**`ctrl+shift+2`（Update Changelog）**:
   1. `[Unreleased]` が空なら、前のリリース（最新のタグ `v*`）以降のコミットから生成した内容を確認する（`Enter` = 書き込んで続行 / `e` = 書き込んで編集 / `n` = 中止）。
      - 載せる種類: `feat` → 追加、`fix` → 修正、`refactor`・`perf`・種類なし → 変更。載せない種類: `docs`・`test`・`chore`・`ci`・`style`・`build`・`Release v…`・`Merge …`。
      - コミットの 1 行目が、そのまま文になる（先頭の決定番号 `D177 ` は外す）。**利用者に分かる文に、後で直す**。
   2. 次の版を選ぶ（1 = パッチ / 2 = マイナー / 3 = メジャー / `x.y.z` を直接入力）。
   3. `package.json` の `version` を更新し、`CHANGELOG.md` の `[Unreleased]` を `[x.y.z] - 日付` に切り出す（末尾の比較リンクも更新）。
3. `CHANGELOG.md` の文を確認・編集する（コミットはまだしなくてよい）。
4. **`ctrl+shift+3`（release-tag-and-push-short）**:
   1. 前提の確認: 版の節が `CHANGELOG.md` にある・タグが未作成（ローカル・リモート）・`main` ブランチ・`origin/main` より遅れていない・`package.json` と `CHANGELOG.md` 以外に未コミットの変更がない。
   2. 公開前の検査（`check:release`）。
   3. 確認（`Enter` = 実行 / `n` = 中止）→ `Release vX.Y.Z` をコミット → `main` を push → 注釈付きタグ → タグを push。
5. **以降は、Actions が自動で行う**（`.github/workflows/release.yml` → `deploy.yml`。数分）:
   1. 版の検証（タグ = `package.json` の version・タグのコミットが `main` に含まれる）。
   2. `CHANGELOG.md` から、その版の節を抽出して、**GitHub Release を作成**。
   3. HoYoLAB 取り込みの拡張機能（`extension/hoyolab-importer`）の zip（Chrome 用）を、Release に添付。Firefox 用は、その版（拡張機能の `manifest.json` の `version`）が**未署名のときだけ**、AMO で署名して、署名済みの `.xpi` を添付（下の「Firefox 版の拡張機能（署名・配布）」）。
   4. **deploy（GitHub Pages への公開）を起動**（タグのソースをビルド → `check:release` → 公開）。署名済みの `.xpi` は、deploy が Release から取得して、公開サイトに同梱する。
6. 公開サイトで、フッターの「バージョン v<版>」と、「gcsim で計算」の動作を確認する。

事前の確認だけをしたいときは、タスク `release-tag: dry run`・`Update Changelog: dry run`（何も実行・変更しない）。

## 最初のリリース（v1.0.0）
- `package.json` は `1.0.0`、`CHANGELOG.md` に `[1.0.0]` の節があり、タグが未作成なので、**`ctrl+shift+2` は不要**（実行しても、「`ctrl+shift+3` でリリースできます」と案内される）。
- 先に、未コミットの変更（`.github/workflows/`・`.vscode/`・`scripts/` など）を、コミットして `main` に push する。
- その後、`ctrl+shift+3`。

## なぜ、タグの push から deploy を直接起動しないか
`github-pages` 環境は、既定で `main` ブランチからのデプロイだけを許可する（タグ起点の deploy は、保護ルールで拒否される。2026-10-12 に確認）。
そのため、タグ起点の `release.yml` が、`gh workflow run deploy.yml --ref main -f ref=<タグ>` で、**main の上で**deploy を実行する（公開するソースは `ref` でタグを指定）。環境の保護ルールを緩めずに済む。
（Actions の `GITHUB_TOKEN` による `workflow_dispatch` は、許可されている。`release.yml` に `permissions: actions: write` を指定している。）

## 手動での公開（予備）
Actions の `deploy` → Run workflow（ブランチ `main`。`ref` に、公開したいタグを入れる。空なら main の先頭）。

## Firefox 版の拡張機能（署名・配布）
HoYoLAB 取り込みの拡張機能の Firefox 版は、**AMO（Mozilla のアドオンのサイト）で署名した `.xpi`** を、**非公開（unlisted。自分で配布する）**で配る（2026-11-18 決定。[issue #60](https://github.com/gwin7ok/Genshin-Rotation-Planner/issues/60)・`docs/hoyolab-import/plan.md`）。Firefox の正式版は、署名のない拡張機能を常設できない。署名は、人の審査を待たない（自動の検査だけ）。

### 全体の流れ（自動）
1. `ctrl+shift+3` でタグを push → `release.yml` が、Release を作り、Chrome 用の zip を添付する。
2. 続けて、**拡張機能の版（`extension/hoyolab-importer/manifest.json` の `version`）が未署名なら**、`npm run ext:pack` で Firefox 用（`build/extension/firefox/`）を作り、`web-ext sign --channel unlisted` で署名して、`grp-hoyolab-importer-<版>.xpi` を Release に添付する。**署名済みの版（どれかの Release に、同じ名前の `.xpi` がある）は、飛ばす**。
3. `deploy.yml` が、画面をビルドする前に、`npm run ext:fetch-signed` で、Release にある**いちばん新しい署名済みの `.xpi`** を取得して、公開サイトの `downloads/` に置く:
   - `grp-hoyolab-importer.xpi` … 最新（固定名。アプリの導入の案内が指す）
   - `grp-hoyolab-importer-<版>.xpi` … 同じファイル（更新用 JSON が指す）
   - `grp-hoyolab-importer-updates.json` … Firefox の**自動更新用**（manifest の `gecko.update_url` が指す。Firefox は 1 日に 1 回ほど見に来て、入っている版より新しければ、更新する）
   署名のあとに deploy を起動するので、更新用 JSON が、まだ無い `.xpi` を指すことはない。

### 最初の 1 回だけの準備
1. AMO（https://addons.mozilla.org/）のアカウントで、開発者ハブの「API 認証情報」（Manage API Keys）から、**JWT issuer** と **JWT secret** を発行する。
   - **JWT secret（JWT 秘密鍵）は、発行（再生成）した直後の 1 回しか、全文が表示されない**。あとからこの画面を開くと、途中が `.....` で省略されていて、その表示をコピーしても、使えない（2026-11-18 に、省略された表示を登録して、署名が通らなかった）。発行した直後に、Secrets に登録し、パスワード管理ツールなどにも控える。
   - 「認証情報を取り消して再生成」をすると、古い鍵は、すぐに使えなくなる。**同じ鍵を使っている他のリポジトリ**（例: firefox-window-resizer）の Secrets も、同時に更新する。
2. このリポジトリの Settings → Secrets and variables → Actions に、`AMO_JWT_ISSUER`・`AMO_JWT_SECRET` を登録する。**値は、画面・ログ・チャット・コミットに出さない**。貼り付けるときに、**値の前後に、空白・改行を入れない**（入ると、AMO の認証が通らない。2026-11-18 の最初の署名で起きた）。
   - 未登録のまま、リリースしても、署名だけが飛ばされて（Actions に警告が出る）、ほかは動く。登録したあとの最初のリリースで、そのときの版が署名される（版を上げ直す必要はない）。
3. 登録した鍵が使えるかは、**リリースをしなくても**、Actions の **`amo-check`**（左の一覧から選び、「Run workflow」）で確かめられる（`.github/workflows/amo-check.yml`・`scripts/check-amo-credentials.ts`）。鍵の値は表示せず、形（長さ・前後の空白・引用符・`user:数字:数字` の形・取り違え・secret に混ざった英数字以外の文字の種類と個数。`●` などのマスク表示をコピーしていないかも分かる）と、AMO での認証の結果（副作用のない問い合わせ）だけを表示する。secret は、前後の空白の有無を変えて 2 通り試す（登録された値のまま、と、空白の有無を逆にした値）ので、「空白が必要か・不要か」も、AMO の答えで分かる（AMO の画面から secret をコピーすると、前後に空白が付くことがあるが、空白は、secret の一部ではないはず）。署名はしない（AMO は、同じ版を 1 回しか署名できないため）。結果は、「登録された値のままで、認証は通りました」なら、鍵は有効。「…なら通ります。登録された値は、通りません」なら、その形で登録し直す。「issuer が、AMO に登録された鍵ではありません」なら `AMO_JWT_ISSUER` を、「issuer は認識されました。secret が、空白の有無にかかわらず、違います」なら `AMO_JWT_SECRET` を、AMO の画面からコピーし直して登録する。
   - 失敗した `release` の**再実行**は、タグの時点のワークフローで動く。そのため、ワークフローを直しても、再実行には反映されない（`amo-check` は、main の最新で動く）。

### 拡張機能を変えたとき（毎回）
- **`extension/hoyolab-importer/` のファイル、または `extension/firefox-manifest-overrides.json` を変えたリリースでは、`extension/hoyolab-importer/manifest.json` の `version` を上げる。** 上げないと、(1) Firefox 版は、その版が署名済みなので署名が飛ばされ、変更が配られない（AMO は、同じ版を署名し直せない）、(2) Chrome 版も、アプリの「拡張機能の新しい版があります」の通知が出ない。
- 拡張機能の版は、アプリの版（`package.json`）とは別に数える。
- **変えてはいけないもの**（配ったあとは変えられない）: 拡張機能の ID（`gecko.id`）、更新用 JSON の URL（`gecko.update_url`）。`strict_min_version`（140）を上げると、古い Firefox の人は、更新できなくなる。
- 確認: `npm run check:extension-manifest`（manifest・更新用 JSON の作り方）・`npm run check:browser-detect`（案内の出し分け）。

### 確認（リリースのあと）
- `https://gwin7ok.github.io/Genshin-Rotation-Planner/downloads/grp-hoyolab-importer-updates.json` が開け、`version` が、署名した版になっている。
- Firefox で、アプリの「持ちキャラ取込」→ `.xpi` をダウンロード → `about:addons` の歯車 →「ファイルからアドオンをインストール」で入る。入ったら、ページを再読み込みして、「拡張機能を検出しました」になる。
- 版を上げたリリースのあと、Firefox の `about:addons` の歯車 →「アドオンの更新を確認」で、版が新しくなる。

### 署名が自動でできなかったとき（手動の署名）
1. `npm run ext:pack` で、`build/extension/firefox/` を作る。
2. AMO の開発者ハブで、新しい版を提出する（「自分で配布する」= unlisted。`build/extension/firefox/` の中身を zip にして、アップロード）。
3. 署名済みの `.xpi` をダウンロードし、**`grp-hoyolab-importer-<版>.xpi`** という名前にして、その版の Release の Assets に添付する（手でも、`gh release upload <タグ> <ファイル>` でもよい）。
4. Actions の `deploy` を、手動で実行する（上の「手動での公開（予備）」）。

## gcsim のバージョンを上げるとき
`docs/gcsim-サーバー更新手順.md`（6-B: WASM の再ビルドとフォークのタグ `app-wasm-<gcsim の版>`）を行ってから、上の流れ（副を上げる）に進む。
同梱のプリセット編成（`src/data/presets/*.json`）の反応の行は、gcsim のバージョンが違うと出なくなる（古い結果を出さないため）。必要なら、画面で「gcsim で計算」→ 保存 → JSON を書き出し → 同名のファイルを置き換える（`exportedAt` は消す）。

## 失敗したとき
| 症状 | 対処 |
|---|---|
| `ctrl+shift+3` が、「タグがすでにある」と止まる | 版を上げる（`ctrl+shift+2`）。タグの再作成・削除はしない（公開した版は、付け直さない） |
| Actions の `release` が、「タグが package.json と違う」で失敗 | タグを付けた後に、`package.json` を変えた。新しい版で、やり直す |
| `release` の「deploy を起動」が 403 | リポジトリの Settings → Actions → General → Workflow permissions を確認。予備の手動の公開（上）で公開する |
| `deploy` の `check:release` が、フォークのタグで失敗 | `docs/gcsim-サーバー更新手順.md` の 6-B（`app-wasm-<版>` のタグ） |
| Release はできたが、公開されない | Actions の `deploy` の結果を確認。直したら、予備の手動の公開 |
| `release` の「Firefox 版の拡張機能を…署名」が失敗（`release` が赤く表示される。**アプリの公開（deploy）は、起動される**。Firefox 版だけが、署名されないまま） | ログを確認する（鍵の間違い・AMO の障害・manifest の検査の指摘など）。直したら、Actions で、失敗した `release` を再実行する（Release は作り直さず、署名のところからやり直す）。AMO が署名を済ませていて、添付だけ失敗したときは、再署名できないので、「署名が自動でできなかったとき（手動の署名）」の 3 から |
| 署名のログに `Upload failed: Unauthorized`・`Error decoding signature` | AMO の API 認証情報（鍵）が合っていない。多くは、`AMO_JWT_SECRET`（または `AMO_JWT_ISSUER`）の値の**前後に、空白・改行が入っている**（ログの `env:` の表示で、`AMO_JWT_SECRET:  *** ` のように、`***` の前後に余計な空白が見えるときは、これ）、または、値の取り違え（issuer と secret が逆）・AMO で鍵を作り直したあとに、古い値のまま・**AMO の画面の、途中が `.....` で省略された secret の表示をコピーして登録した**（secret の全文は、発行した直後の 1 回しか表示されない。「最初の 1 回だけの準備」）。AMO の「API 認証情報」から値をコピーし直し、**前後の空白・改行を入れずに**、Secrets を登録し直して、失敗した `release` を再実行する。**どちらの値が違うかは、Actions の `amo-check`（手動起動。下記）で調べられる**（AMO は、issuer が違うと `Unknown JWT iss (issuer).`、issuer は合っていて secret が違うと `Error decoding signature.` を返す）。鍵を AMO で取り消して作り直すと、同じ鍵を使う他のリポジトリが動かなくなるので、まず `amo-check` で、どちらの値が違うかを確かめる |
| `release` に「Firefox 版の署名を飛ばしました」の警告 | Secrets（`AMO_JWT_ISSUER`・`AMO_JWT_SECRET`）が未登録。登録すれば、次のリリースで署名される |
| アプリの Firefox の案内の「ダウンロード」が 404 | 署名済みの `.xpi` が、公開サイトに無い（まだ署名していない）。上の 2 つを確認し、署名されたら、Actions の `deploy` を手動で実行する |

## 更新の通知（利用者のブラウザ）
- **判定は、アプリの版ではなく、DB（マスターデータ）のバージョン（`src/data/databaseMaster.ts` の `DATABASE_VERSION`）で行う**（D198）。ブラウザに、利用者が最後に確認した DB のバージョン（`app_last_seen_db_version`）を記録する。ページの読み込み時に、今の `DATABASE_VERSION` のほうが新しければ、「DB管理で、キャラ・武器・聖遺物のマスターデータを、全削除 → 動的生成してください」というポップアップを、1 度だけ出す（`src/utils/versionNotice.ts`・`UpdateNoticeModal.tsx`）。
- **運用ルール: 同梱のマスターデータの内容・構造を変えたら、`DATABASE_VERSION` を上げる**（もともとの運用。上げると、保存 DB の同梱マスターへの自動の置き換えと、この通知の両方が働く。1 つの番号に統一している）。アプリの版（x.y.z）は、通知に関係しない。
- 記録がない利用者（この機能の導入前から使っている人）は、保存 DB の `version` で判定する（今と同じなら出さない）。自動の置き換えで `version` が書き換わる前に、`loadDatabase` が、記録として残す。
- 初めての利用者（DB がない）には出さない（同梱の最新のマスターが使われるため）。古いアプリを開いたときは、記録を進めない。
- 確認: `npm run check:version-notice`。

## 注意
- `package.json` の `version` は、`npm version` ではなく、Update Changelog で変える。
- 公開した版のタグは、消さない・付け直さない（フォークの `app-wasm-*` タグも同じ）。
- Release を作る Actions と、公開の Actions は別の実行。**Release が先に作られ、公開は数分後**に終わる。
- Firefox 版の `.xpi` は、リポジトリに入れない（`build/`・`public/downloads/` は Git の対象外）。署名済みのファイルの原本は、Release の Assets。
