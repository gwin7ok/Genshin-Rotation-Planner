# 公開サイトの構築・デプロイの実装計画（静的配信 + ブラウザ内 WASM）

状態: **計画（2026-10-12 に全面改訂。D169 の WebAssembly 化を反映。デプロイは未実施・ユーザーの指示を待つ）**
作成: 2026-09-30 / 改訂: 2026-10-12

> 旧計画（gcsim サーバーを公開側で動かし、リバースプロキシで制限する方式）は、**破棄した**。gcsim をブラウザの中の WebAssembly で動かす（D169）ので、公開側が動かす処理は無い。旧計画の「リバースプロキシの制限・systemd の gcsim 常駐・UFW の gcsim 向けの設定」は不要になった。

## 1. 構成

```
ブラウザ ──https://<サイト>/──▶ 静的ファイルの配信だけ
                                ├ /                    画面（npm run build の dist/）
                                ├ /assets/*            画面の JS・CSS（ハッシュ付きの名前）
                                ├ /data/*.json         実行時に読む固定データ（辞書・キー表）
                                └ /gcsim/              worker.js・wasm_exec.js・main.wasm・wasm-info.json
```

- サーバー側の計算は無い。利用者のデータ（編成・ローテーション）は、ブラウザの localStorage に保存される。サーバーに何も送らない（設定文も、ブラウザの中の Worker が処理する）。
- 利用者の手間は、URL を開くだけ（初回だけ、約 5.7 MB〔brotli〕の WASM を読み込む。以後はキャッシュ）。
- 画面が外部から読むのは、アイコン画像（`https://enka.network/ui/…`）だけ。

## 2. 配信先の選択肢

| 案 | 長所 | 短所 |
|---|---|---|
| **A. GitHub Pages**（推奨候補） | 無料・運用なし・CDN・HTTPS・自宅の IP を出さない・GitHub Actions で自動デプロイできる（ビルドの記録が残る） | 1 サイト 1 GB・月の転送量の目安 100 GB（1 訪問 約 6 MB なら、月 約 1.6 万訪問が目安）。ヘッダー（`Cache-Control`）を自由に付けられない。プロジェクトサイトは `/<リポジトリ名>/` の下になる（`base` の設定が要る） |
| **B. 自宅の Ubuntu + Caddy / nginx**（旧計画の延長） | ヘッダー・圧縮・ドメインを自由に決められる | 自宅回線の上りが、1 訪問 約 6 MB のたびに使われる。ポート開放・DDNS・証明書の運用・自宅 IP の公開。停止（電源・回線）のリスク |
| C. Cloudflare Pages | 無料・CDN | **1 ファイル 25 MiB の上限があり、`main.wasm`（44 MB）を置けない**（圧縮前のサイズで判定）。R2 など別の置き場が要る |
| D. 他の静的ホスティング（Netlify・Vercel など） | 運用なし | 転送量・ファイルサイズの制限は、利用前に確認する |

推奨: **A（GitHub Pages）で始め、転送量・ヘッダーの制約が問題になったら B（または R2 + カスタムドメイン）へ**。静的ファイルだけなので、移行は、ファイルを置き換えるだけ。

## 3. 実装項目

### A. ビルドの手順（どの配信先でも共通）
1. `npm ci`
2. `npm run wasm:build`（Go 1.27 以上。`gcsim.config.json` のコミットのソースから、`public/gcsim/` に `main.wasm`・`wasm_exec.js`・`wasm-info.json` を生成。ソースの取得は `codeload.github.com`）
3. `npm run build`（`dist/` に、`public/` ごと出力される）
4. **ビルドの検査**（デプロイの前）:
   - `dist/gcsim/main.wasm` が存在し、SHA-256 が `wasm-info.json` と一致する。
   - `wasm-info.json` の `gcsimCommit` が、`gcsim.config.json` の `commit` と一致する（WASM の作り直し忘れの検出）。
   - `gcsim.config.json` の `sourceMirror` のタグ（`app-wasm-<version>`）が、フォークに存在し、`commit` を指している（`gh api repos/<フォーク>/git/ref/tags/<タグ>`）。AGPL のソースの控えが欠けた版を、公開しない。
   - `npm run check:snapshots`・`npm run gcsim:check`。

### B. GitHub Pages で配信する場合の設定
- `vite.config.ts` の `base` を、デプロイ先の URL のパスに合わせる（`/Genshin-Rotation-Planner/` など。独自ドメインなら `/`）。環境変数（`VITE_BASE`）で渡せるようにする。コードは、`import.meta.env.BASE_URL` を使っている（`gcsimWasm.ts`・`runtimeData.ts`）。他の絶対パスが無いかを、デプロイ前に画面で確認する。
- GitHub Actions のワークフロー（`.github/workflows/deploy.yml`。タグ・手動で起動）: `actions/setup-go` → 上記 A の手順 → `actions/upload-pages-artifact` → `actions/deploy-pages`。
- SPA のフォールバックは不要（URL は 1 つだけ）。

### C. 自宅の Ubuntu で配信する場合の設定（B 案）
- Caddy の例: `file_server { precompressed br gzip }` と、`/gcsim/*`・`/data/*` の `Cache-Control: no-cache`、`/assets/*` の `Cache-Control: public, max-age=31536000, immutable`。
- 事前に圧縮ファイルを作る（`main.wasm.br`・`main.wasm.gz`。動的圧縮は 44 MB では重いので避ける）。
- `Content-Type: application/wasm`（既定で付く。付かなくても、Worker は予備の経路で動く。ただし、ストリーミング読み込みより遅い）。
- ポート・DDNS・証明書（DNS-01）は、旧計画のとおり（高番号ポート + DDNS。将来 Cloudflare Tunnel）。**ポートの番号・DNS 事業者は、実施するときに決める**。
- ファイアウォールは、公開ポートと SSH だけ許可する。

### D. キャッシュの扱い（重要）
- `main.wasm`・`worker.js`・`wasm_exec.js` は、**名前にハッシュが付かない**。古いキャッシュが残ると、画面（新）と WASM（旧）の版がずれる。
  - 対策 1: `/gcsim/*` を、`Cache-Control: no-cache`（毎回、ETag で確認。変わっていなければ 304 で、再取得しない）にする。GitHub Pages は、既定で `max-age=600`（10 分）なので、更新直後の 10 分間は、旧版が使われる可能性がある。許容するか、対策 2 にする。
  - 対策 2: 起動時に `wasm-info.json` を取得し、`GCSIM_COMMIT` と比べる（下の E）。食い違えば、再読み込みを促す。
- `/data/*.json` は、アプリ側が `cache: 'no-store'` で読む（変更なし）。

### E. バージョンの食い違いの検出（旧計画の D の置き換え）
- 目的: 画面（`gcsim.config.json` のコミット）と、配信している WASM（`wasm-info.json`）の版のずれを、画面で気づけるようにする（辞書・マスターと WASM の版がずれると、キャラが動かない・結果がずれる。2026-09-30 にサーバー版で実際に発生した）。
- 内容: 起動時に `${BASE_URL}gcsim/wasm-info.json` を取得し、`gcsimCommit` を `GCSIM_COMMIT` と比べる。食い違えば、画面に警告を出す（「gcsim の版が合っていません。ページを再読み込みしてください」）。取得できないとき（開発環境の localhost サーバー・オフライン）は、何も出さない。
- 完了条件: `wasm-info.json` を、意図的に別のコミットにして、画面に警告が出る。

### F. 画面の表示・ライセンス（実装済み。D169）
- フッター（非公式表示・AGPL・アプリのソース・gcsim のソースとコミット）: `SourceNotice.tsx`。
- `LICENSE`（AGPL-3.0 全文）・`NOTICE`（gcsim の WASM の配布の記述）。
- 残り: 利用規約・プライバシーの短い説明（「サーバーには何も送らない。編成はブラウザの localStorage に保存される」）。フッターに足す。

### G. セキュリティ設定（任意。公開前に検討）
- CSP の例: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; img-src 'self' https://enka.network data:; connect-src 'self'`（WebAssembly の生成には `'wasm-unsafe-eval'` が要る。Tailwind などのインラインスタイルがあれば、`style-src 'unsafe-inline'`）。GitHub Pages ではヘッダーを付けられないので、`<meta http-equiv>` で代用できる範囲に限る。
- 配信するのは静的ファイルだけで、サーバー側の攻撃面は小さい。

### H. Google Drive 保存（将来）
- 保存層（localStorage の読み書き）を 1 か所にまとめておく（別途。D169 の次の作業）。Google の OAuth には、リダイレクト URI が要るので、公開 URL が決まってから設計する（クライアント ID の設定。`drive.file` スコープだけ。サーバー側のコードは不要）。

## 4. 実装の順序（案）
1. E（版の食い違いの検出）と、F の残り（利用規約・プライバシーの説明）— 画面の変更だけ。
2. A の検査をスクリプト化（`npm run check:release`）。
3. 配信先を決める（A 案か B 案）。
4. A 案なら B（`base`・ワークフロー）。B 案なら C（Caddy / nginx の設定・事前圧縮）。
5. 公開 → 実機（別のブラウザ・スマホ）で、「gcsim で計算」と文法チェックを確認。
6. 将来: Google Drive 保存・ネイティブアプリ（2-C）。

## 8. 配信先の方針と、将来の移行（ユーザー決定 2026-10-12。D171）

- **最初は GitHub Pages で公開する**（`https://<アカウント>.github.io/<リポジトリ名>/`。費用 0 円）。**商用化する段階で、別のサービスに移行する**（Pages は、商用の SaaS・オンラインビジネスの提供を目的としていないため）。
- **独自ドメインは使わない**。そのため、移行すると URL（オリジン）が変わり、**利用者のブラウザの localStorage（保存した編成）は引き継がれない**。
- **移行時の救済**: 旧サイトに「**引っ越しのお知らせ**」を出し、**JSON の書き出し・読み込み（既存機能）で、編成を移してもらう**。
  - お知らせの内容: 新しい URL・移行の期日・手順（旧サイトで「JSON 書き出し」→ 新サイトで「JSON 読み込み」）。
  - 旧サイトは、移行後もしばらく残し、お知らせだけを表示する版に置き換える（移行に必要なら、書き出しの機能は残す）。
  - 実装は、移行を決めたときに行う（今は不要）。ただし、**JSON の書き出し・読み込みが、全編成・保存スロットを含めて往復できること**を、移行の前に確認する。
- **移行の前提になる設計**: Google Drive 保存（将来）を入れると、OAuth のリダイレクト URI・承認済みオリジンが URL に紐づく。**Drive 保存を入れる前に移行を済ませる**か、移行のときに OAuth 設定を作り直す。
- 移行先の候補（商用化のとき）: Cloudflare R2 + カスタムドメイン（Pages は 1 ファイル 25 MiB の上限で `main.wasm` を置けない）、自前の VPS、ほか。商用化の前に、ゲームの権利物（HoYoverse のファンコンテンツの方針）と、AGPL のソース提供の義務を確認する。
- `base` は、デプロイ先の URL のパス（`/<リポジトリ名>/`）に合わせる（B）。

### 8-A. JSON の往復の確認結果（2026-10-12。コードの調査。D172）

移行の救済に、既存の JSON 書き出し・読み込み（`SaveLoadModal.tsx`）だけで足りるかを調べた。**1 つの編成の往復は、ほぼ損なわれないが、利用者のデータ全体は移せない**。

| データ | 保存先（localStorage） | JSON で移せるか |
|---|---|---|
| 編成 1 つ（パーティ・出場・ループ・交代の遅れ） | `genshin_rotation_current_state_v2` / 各スロット | **移せる**。書き出しは「保存編成 1 つ」または「現在の編成」を 1 ファイル。ファイルの読み込みは、同名があれば連番を付けて、保存編成として登録する |
| 保存編成（スロット）の全部 | `genshin_rotation_saved_slots_v2` | **1 つずつしか書き出せない**（一括の書き出し・読み込みが無い）。スロットが多い人は、手間が大きい |
| 設定（防御ヒットストップ・敵から受けるダメージ・記法の表示） | `gcsimDefHalt`・`gcsimHurt`・`rotationNotationMode` | **移せない**（JSON に含まれない） |
| データベース（キャラ・武器・聖遺物のマスターと、利用者の編集・追加分） | `genshin_app_db_v1` | **移せない**。マスターは、新サイトで再生成されるが、**利用者が編集・追加したデータ（`isCustom`）は失われる** |
| 画面の貼り付けからの読み込み | — | **交代の遅れ（`switchDelay`）が失われる**（既定の 0.5 秒になる）。説明（`description`）は、どちらの読み込みでも読まれない |

**移行を決めたときに必要な作業（候補）**
1. **全データのバックアップ（一括の書き出し・読み込み）**を追加する: 全スロット + 現在の編成 + 設定 + 利用者が編集・追加したデータを、1 つの JSON ファイルにする（版の番号つき）。引っ越しのお知らせから、1 クリックで書き出せるようにする。
2. 貼り付けからの読み込みで、`switchDelay` と `description` を読むようにする（小さな修正）。
3. 往復のテスト（書き出し → 全データ削除 → 読み込み → 全スロット・設定が同じ）を、スナップショット等で確認する。
4. 移行より前に、Google Drive 保存の設計を入れるなら、同じ「全データのバックアップ」の形式を使う（保存層を 1 か所にまとめる作業と一緒に行う）。

## 9. デプロイの準備（2026-10-12 実装済み。D173）

- `vite.config.ts`: `base` を、環境変数 `VITE_BASE`（未指定は `/`）で指定する。
- `.github/workflows/deploy.yml`: Actions タブから手動（Run workflow。ブランチは main）で起動する（タグの push では、github-pages の環境の保護ルールで失敗する。2026-10-12 に確認）。流れは、`npm ci` → `npm run wasm:build`（Go 1.27.2）→ `npm run check:snapshots` → `npm run build`（`VITE_BASE=/<リポジトリ名>/`）→ `npm run check:release` → Pages に公開。**フォークのタグが無い版は、`check:release` で止まる**（AGPL）。
- 確認: `VITE_BASE=/Genshin-Rotation-Planner/` で本番ビルドし、`vite preview` で、`/Genshin-Rotation-Planner/` の下で、画面・データ・WASM が読み込まれ、「gcsim で計算」が動くことを確認した。
- **ローカル（Windows の Git Bash）で `VITE_BASE=/…` を渡すときは、`MSYS_NO_PATHCONV=1` を付ける**（付けないと、`/Program Files/Git/…` に変換される）。Actions（Linux）では不要。
- **公開の手順（ユーザーの作業）**: ① リポジトリの Settings → Pages → Source を「GitHub Actions」にする ② Actions タブの「deploy」を手動で実行する（Run workflow・ブランチ main）③ 公開された URL（`https://<アカウント>.github.io/<リポジトリ名>/`）で、「gcsim で計算」を確認する。

### 8-B. 全データのバックアップ（2026-10-12 実装済み。D174）

8-A の不足を解消した。「編成管理」→「JSON バックアップ・共有」タブの先頭に、**「全データを書き出す」「バックアップから復元する」**を追加した。

- 形式: `{ format: 'genshin-rotation-planner-backup', version: 1, currentState, savedSlots, settings, database }`（`src/utils/backup.ts`。Google Drive 保存も、この形式を使う）。
- 含める: 現在の編成・保存編成（全件）・設定（防御ヒットストップ・敵から受けるダメージ・記法の表示）・利用者が作成・ロックしたキャラ・武器・聖遺物。含めない: マスター（新しい版で再生成される）。
- 復元の規則: 保存編成は ID で突き合わせ、バックアップのほうが新しいときだけ置き換える（無い ID は足す）。現在の編成・設定・データベースの項目は、バックアップのもので置き換える。確認の後、画面を再読み込みする。
- 貼り付けからの読み込みで、交代の遅れ（`switchDelay`）・所要時間を落とす不具合も修正した。
- 確認: `npm run check:backup`（15 項目。往復・規則・拒否）。実アプリでも、保存編成 7 件・現在の編成・設定を全消去 → 復元して、保存編成は完全一致、現在の編成・設定も一致することを確認した。
- **移行のときの「引っ越しのお知らせ」は、このボタンを案内するだけでよい**（お知らせの画面は、移行を決めたときに実装する）。

### 8-C. 保存層の整理（2026-10-12 実装済み。D175）

ブラウザの localStorage の読み書きを、`src/utils/persistence.ts` の 1 か所に集めた。

| ファイル | 役割 |
|---|---|
| `persistence.ts` | 低レベルの読み書き（`readString`・`writeString`・`readJson`・`writeJson`・`removeKey`）。失敗（容量超過・無効）は例外にせず、戻り値で返す。保存先（バックエンド）を差し替えられる（`setPersistenceBackend`）。キーの一元管理: `STORAGE_KEYS`（編成・保存編成・データベース）・`SETTING_KEYS`（利用者の設定。バックアップに含める）・`DEVICE_KEYS`（この端末だけの設定。含めない） |
| `appSettings.ts` | 型のある設定の読み書き（防御ヒットストップ・敵から受けるダメージ・記法の表示） |
| `storage.ts` | 現在の編成・保存編成（スロット） |
| `databaseService.ts` | データベース（マスター + 利用者のデータ） |
